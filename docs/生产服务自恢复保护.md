# 生产服务自恢复保护

更新时间：2026-09-02。

本文说明 `site-platform.service` 的保守自恢复、发布维护锁和验收方式。它用于防止主机包维护、
依赖服务短暂停止或后端异常退出后长期遗留 `502`，但不替代发布前备份、数据库迁移门禁、业务冒烟
或人工回滚判断。

## 一、保护边界

保护由六层组成：

1. `site-platform.service` drop-in 使用 `Restart=on-failure`，只处理进程异常退出；人工
   `systemctl stop` 不会被这一策略自动反向启动。
2. `site-platform-watchdog.timer` 每分钟触发一次保守检查。它只在 MySQL、Redis 均为 `active`，
   APT 自动升级任务未运行，且不存在发布维护锁时，尝试启动一次 `inactive/failed` 的后端。
3. 所有非 dry-run 的生产写阶段（`05`、`10`、`15`、`20`、`25`、`30`、`40`、`50`、`55`、`60`
   和 `90`）都在动态校验或写入前取得固定发布操作锁 `/run/site-platform-release.lock`，并持有到脚本
   进程退出，防止激活、回滚、迁移或证据写入并发执行。
4. 停服和回滚脚本还会取得 watchdog 共用的固定协调锁 `/run/site-platform-watchdog.lock`，再创建固定维护锁
   `/etc/site-platform/maintenance.lock`。锁与本次同点备份目录、服务名的 SHA-256 绑定，不保存
   数据库密码、业务密钥或备份路径明文。
5. `10`/`90` 在维护锁建立后先关闭并核验 `site-platform.service` 开机自启，再停止服务；`40`/`90`
   只有在完整健康门禁通过后才重新启用开机自启并解除维护锁。核验只接受精确的持久
   `enabled`，不把 `enabled-runtime/static/alias/indirect/generated` 当作开机自启。因此意外重启不会把半迁移 JAR 自动拉起。
6. `30` 的 systemd transient worker 使用 `/run/site-platform-offline-worker.state` 记录
   `SUBMITTING/RUNNING` 生命周期，并使用固定 sidecar 租约 `/run/site-platform-offline-worker.lock`
   串行化状态切换、残留判定和标记删除。所有其他生产写阶段都会拒绝与它并发；SSH 断开后实际 Java worker
   仍受 systemd 和该标记保护，不能因调用端的发布锁消失而放行迁移或回滚。

watchdog 不会对正在运行但健康异常的后端执行 `restart` 或 `try-restart`，避免在数据库阻塞、外部依赖
抖动或业务慢请求期间制造第二次中断。此类情况只记录告警，继续由人工诊断。

## 二、安装与核验

必须先确认现有后端、MySQL、Redis 和本机验证码接口健康，再从已验签的生产更新包执行：

```bash
bash ops/05-self-heal-control.sh install
bash ops/05-self-heal-control.sh verify
```

安装脚本会校验包内资产、原子安装 systemd drop-in、watchdog unit/timer 和只读健康脚本，随后
`daemon-reload` 并启用 timer。它会比较安装前后的主服务 `InvocationID` 和 `MainPID`，不得停止、重启
或替换正在运行的后端进程。

如果目标文件已存在且内容不同，默认拒绝覆盖。只有逐文件核对差异并明确授权后，才允许：

```bash
bash ops/05-self-heal-control.sh install \
  --replace --confirm REPLACE_SITE_PLATFORM_SELF_HEAL
```

脚本会在真正替换前把旧文件保存到 `/var/backups/site-platform-self-heal/`。安装和核验都会先等待并取得
`/run/site-platform-release.lock`；如另一个生产阶段正在执行，命令等待属于正常串行化，不是卡死。
安装或核验时如发现生产维护锁仍存在，必须先完成原发布或同点回滚，不得绕过锁启用保护。

## 三、维护锁生命周期

- `/run/site-platform-release.lock` 是整个生产写阶段的排他租约。文件本身可以在命令结束后继续存在，
  真正的锁由内核随持锁进程退出自动释放；禁止删除该文件来“解锁”，也不要并行开第二个发布或回滚命令。
- `10-stop-and-backup.sh` 在第一次停后端前，先等待已经运行的 watchdog 退出同一把 `/run` 协调锁，
  再原子创建维护锁，并一直持有协调锁到主服务确认停止；已有锁、软链锁、字段被篡改、权限/属主不符
  或绑定到其他备份目录时均拒绝继续。
- `10` 创建维护锁后立即 `disable` 主服务并核验，再停服；`15`、`20`、`25`、`30`、transition `50`
  和 `40` 每一步都重新验证同一把锁、服务停机状态和 `disabled` 状态。“停机”必须同时满足
  `LoadState=loaded`、`ActiveState=inactive/failed`、`MainPID=0`、`ControlPID=0` 且无 systemd job；
  `activating/deactivating` 不得当作已停稳。
- 新后端通过本机、公网、API 文档关闭和启动日志门禁后，`40-activate-backend.sh` 先恢复并核验主服务
  开机自启，随后才解除锁。
- `90-rollback.sh` 同样通过 `/run` 协调锁串行化维护锁的创建/核对，关闭开机自启后才停后端；只有旧
  系统完成同点恢复并通过本机和公网健康门禁、重新启用开机自启后才解除锁。
- 任一迁移、激活或回滚失败都保留锁。锁没有 TTL，也不会按时间自动删除。
- 正常在线状态必须保持 `site-platform.service` 开机自启；维护窗口内则必须保持 `disabled`。`10`
  正式执行前会拒绝 APT `Automatic-Reboot=true`、APT 配置无法可靠读取或已有 `/run/reboot-required`
  的主机；从创建维护锁到 `40/90` 健康解锁期间，仍禁止执行 ECS 重启、`reboot` 或安排其他自动重启。

若维护窗口内发生意外重启，先视为半迁移事故：主服务应因 `disabled` 保持停止；仍要核对
`systemctl is-enabled/is-active site-platform.service`。如意外为 `active`，立即停止；保持 Nginx 后端流量
不可用，核对维护锁绑定、同点备份、当前表数/迁移标记、离线 worker 标记和 JAR/Web 软链，再决定从
精确停点继续或执行 `90-rollback.sh`。不得删除维护锁或直接恢复流量。

禁止直接 `rm /etc/site-platform/maintenance.lock`，也禁止删除 `/run/site-platform-release.lock` 或
`/run/site-platform-watchdog.lock` 来绕过串行门禁。如果健康系统已经恢复但脚本因文件系统异常未能删除
维护锁，应先修复权限/挂载问题，再从同一已验签更新包进入受控 shell：先调用
`acquire_release_operation_lock` 取得全程互斥租约，再用 `assert_maintenance_lock` 核对原备份绑定，确认
主服务为 `active` 且 `wait_for_backend_health` 的本机和公网两级门禁通过，再执行并核验
`systemctl enable site-platform.service`，最后才能调用 `release_maintenance_lock`。任一步失败都保留
维护锁并改走同点回滚。

## 四、离线 worker 断连与残留恢复

`30-visitor-reencrypt.sh` 在提交 transient unit 前原子写入 `SUBMITTING`。root 包装器真正接管后才把
它原子切换为 `RUNNING`，随后降权为 `site-platform` 执行 Java；正常退出和可捕获的前置失败都会清理
匹配标记。包装器的切换/自检与自动复核、`06` 故障恢复共用固定 sidecar 租约，防止
复核方在 `SUBMITTING -> RUNNING` 交接中误删新标记。调用端断连时标记继续存在：排队中的
systemd job、已加载 unit、非零 PID 或 `RUNNING`
状态都保持 fail-closed。只有 `SUBMITTING` 且 systemd 明确报告 unit `not-found`、无 job、`MainPID=0`
时，下一生产阶段才可自动清理未提交标记。

正式 `EnvironmentFile` 中保持 `APP_SCHEDULING_ENABLED=true`；systemd 的 EnvironmentFile 会覆盖普通
`Environment=`/`--setenv`。因此 `30` 不依赖 `--setenv` 关闭调度，而是在 EnvironmentFile 已加载后由
root wrapper 最终执行 `/usr/bin/env APP_SCHEDULING_ENABLED=false ... java`，并同时覆盖离线 Profile 和
VERIFY/APPLY 控制量。正式数据库、JWT 和加密密钥仍只从 EnvironmentFile 继承，不进入命令参数。

如果 wrapper 被 `SIGKILL`/OOM，`RUNNING` 标记会故意保留。先查看精确 unit 和日志，不得直接删除：

```bash
sudo sed -n '1,2p' /run/site-platform-offline-worker.state
sudo systemctl status '<标记中的UNIT_NAME>.service' --no-pager -l
sudo journalctl -u '<标记中的UNIT_NAME>.service' --no-pager
```

确认 unit 已彻底停止，复核本次 `30` 日志及数据库是 `98/24/0` 或 `98/25/1`，并使用原同点备份执行：

```bash
sudo bash ops/06-offline-worker-recovery.sh \
  --backup-dir /root/backups/dianxinyun/<本次同点备份> \
  --confirm CLEAR_STALE_OFFLINE_WORKER_AFTER_DATABASE_REVIEW
```

该命令取得专用发布锁，核对维护锁、主服务停止且 `disabled`、unit 无 job/PID 和数据库精确状态后，
只清理与记录 unit 匹配的标记。若数据库为 `98/25/1`，下一步只能 `post-verify`；若为 `98/24/0`，
必须重新 `verify`，不能复用断连前的 APPLY 参数。任一其他状态停止并人工分析，不得强删标记、
删除 `/run/site-platform-offline-worker.lock` 或先回滚；该 lock 文件可以长期存在，真正租约由内核管理。

## 五、只读巡检

```bash
systemctl show site-platform.service \
  -p ActiveState -p SubState -p Restart -p MainPID -p InvocationID -p DropInPaths
systemctl is-enabled site-platform-watchdog.timer
systemctl is-active site-platform-watchdog.timer
systemctl list-timers --all site-platform-watchdog.timer --no-pager
bash ops/05-self-heal-control.sh verify
journalctl -u site-platform-watchdog.service -n 50 --no-pager
lslocks | grep -E 'site-platform-(release|watchdog|offline-worker)\.lock' || true
```

通过标准：主服务、MySQL、Redis 和 timer 均为 `active`，主服务有效 `Restart=on-failure`，本机验证码
HTTP 和业务 `code` 均为 `200`，安装资产与更新包逐字一致。`verify` 是只读操作，不会修复或启动服务。

## 六、自动升级的判定

Ubuntu 的 `apt-daily-upgrade.service` / `unattended-upgrades` 可以按系统配置自动安装安全更新；软件包维护
脚本也可能停止或重启相关服务。仅凭停服时间接近自动更新，不能断言它就是唯一根因。事故复盘应同时
保留 `journalctl`、`/var/log/unattended-upgrades/`、`/var/log/apt/history.log`、systemd unit 状态和
主服务日志，再区分计划维护、包脚本行为、主机重启、人工命令和应用异常。

watchdog 在 APT 升级任务运行期间只跳过，不干预 dpkg/apt。升级完成且依赖恢复后，如果后端确实处于
`inactive/failed`，下一次定时检查才会尝试启动一次。
