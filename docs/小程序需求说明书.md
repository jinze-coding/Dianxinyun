# 小程序需求说明书

## 2026-08-26 固定式临边巡检（现行口径）

- 巡检首页显示“电箱巡检”和“临边巡检”两个独立卡片并分别统计待办数量；进入后使用各自列表，
  个人待办也按两类分区，不把临边任务混进电箱日检。电箱照片、扫码、六项日检及专用月表规则不变。
- 临边任务按点位展示系统固定类型、点位名称、楼栋/楼层/位置说明、唯一执行时段和状态。临边没有
  扫码入口；任务只能由当前明确指派的巡检人执行。
- 表单来自点位类型绑定的系统只读检查表。全部检查项都必须选择“正常”或“异常”，不提供“不适用”；
  每任务至少上传 1 张现场全景照片，正常项不要求说明和单项照片，异常项必须填写说明并上传至少
  1 张证据图，总备注选填。
- 正式提交必须联网，通过 `/api/v1/edge-inspections/tasks/{id}` 重新读取任务并校验有效项目范围、
  `INSPECTION` 模块、`EDGE_INSPECTION_SUBMIT`、当前指派、任务版本及固定检查项快照；任一照片未上传成功时不得提交。
- “临边整改”按任务展示一张整改单。整改人必须为每个异常项填写整改说明并上传至少 1 张整改后照片，
  全部反馈一次提交后进入待复查；复查人只能选择“全部通过并关闭”或“退回整改”，退回原因必填。
  管理者改派整改人或复查人必须填写原因，平台管理员未被指派时也不能直接复查。
- 临边端统一调用 `/api/v1/edge-inspections/**`，任务图片暂存类型为
  `EDGE_INSPECTION_TASK_PENDING`，整改图片暂存类型为
  `EDGE_INSPECTION_RECTIFICATION_PENDING`。首版不展示模板、自定义类别、多时段、备选人、逐点人员
  覆盖、临边二维码、匿名公开月表或导出功能。
- 临边没有项目试点开关。真机验收至少覆盖两类巡检分区、8 类固定表单、照片上传失败、异常必填、
  逾期补检、整单整改、整单通过和退回复查。

## 2026-08-26 图纸及技术文件签收（现行口径）

- 小程序不登记收文或上传超大文件，只承接本人图纸发放待办、精确版本查看下载、
  电子签收、纸质批次扫码、逐文件份数核对、PNG 手写签名及异议。
- 扫码后先由服务端按登录用户、有效项目成员、资料模块、`document.view` 和本人接收记录
  校验，未通过前不返回批次、文件或版本信息。二维码只携带不透明 scene，作废后立即失效。
- `ELECTRONIC` 可从待办明确点击确认；`PAPER / BOTH` 必须扫描技术员展示的批次码。
  `BOTH` 一次纸质领取同时完成电子和纸质签收；任一渠道要求签名时，必须先提交签名。
- 文件、版次或份数不符时只能提交异议，不形成签收。重复扫描已签收批次幂等显示原回执。
- IFC、RVT、DGN 及超大文件不在小程序内在线预览，页面应提示前往 Web 或专业软件下载使用。

## 一、需求来源

需求来源文件：

```text
上海建工电箱检查记录表(2).docx
```

Word 文档中明确的业务内容：

1. 每日电工巡检二级电箱，巡检时扫描电箱二维码，上传电箱外表照片、内部照片。
2. 电工检查完成后，系统自动推送到安全员复核。
3. 现场电箱总数和巡检覆盖范围由项目安全员确定。
4. 安全员现场巡检发现电箱不合规时，也可以扫描二维码，上传问题照片。
5. 安全员发现的问题推送给电工，电工限时 3 天整改。
6. 电工端需要有提示，微信端通知可作为后续增强。
7. 每个电箱和二维码一一对应，并且编号明确。
8. 外部检查或公司检查可以通过微信扫描现场电箱二维码，直接看到巡检记录汇总表。

原检查表字段：

```text
日期 | 内外观 | 漏电保护器 | 熔断 | 保护接零 | 220V插座 | 380V插座 | 检查人 | 备注
```

## 二、产品定位

小程序是“电信云平台项目现场综合管理系统”的现场移动端，首版聚焦电箱检查。

首版目标不是做完整移动端平台，而是先打通一条可落地的现场闭环：

```text
电箱台账
→ 一箱一码
→ 电工扫码日检
→ 正常直接完成 / 异常聚合整改
→ 电工整改
→ 安全员复查关闭或退回
→ 月度汇总
→ 外部检查扫码查看
```

默认技术路线：

- `uni-app + Vue 3 + TypeScript`
- 微信小程序优先
- 复用现有 Spring Boot 后端登录、项目、文件、权限体系

当前阶段边界：

- 小程序首版聚焦电箱巡检，不扩展为完整移动端平台。
- 小程序现场端负责扫码、巡检、整改反馈、复查和查看汇总。
- PC Web 后台负责台账、权限、异常整改管理、汇总导出和公开访问管理。
- 所有项目权限、身份解析和业务状态以后端接口为准。

## 三、首版目标

首版先解决 6 件事：

1. 项目安全员能维护现场电箱台账，明确需要巡检多少个电箱。
2. 每个电箱有唯一编号和唯一二维码。
3. 电工每天扫码巡检电箱，必须分别上传至少一张外观照片和内部照片，并填写检查表。
4. 正常巡检直接完成；异常巡检聚合生成一条整改任务并指派项目电工。
5. 电工提交整改说明和照片后，项目安全员复查关闭、退回或改派。
6. 外部检查或公司检查扫码时，可以查看该电箱巡检汇总。

首版暂不做：

- AI 视频识别。
- BIM 或数字孪生。
- 真实视频流播放。
- 复杂离线巡检。
- 微信一键登录强绑定。
- 企业微信深度集成。
- 订阅消息强依赖。

## 四、用户角色框架

首版不新增全局 `ELECTRICIAN` 角色。“电工”先按项目授权用户或电箱负责人处理。

| 用户 | 主要职责 | 首版说明 |
| --- | --- | --- |
| 平台管理员 | 查看全部项目，管理全局数据 | 可查看、导出所有项目巡检数据 |
| 项目管理员 | 管理授权项目 | 可管理授权项目电箱、巡检、整改 |
| 项目安全员 | 管理电箱台账，复查异常整改 | 必须具备当前项目 `SAFETY_OFFICER + inspection.review` |
| 负责电工 | 扫码日检，处理被指派整改 | 整改人必须具备当前项目 `ELECTRICIAN + inspection.rectify` |
| 外部检查人员 / 公司检查人员 | 扫码查看巡检汇总 | 通过统一码的公开分支免登录查看脱敏汇总，受后台公开访问开关控制 |

权限总原则：

- 所有业务数据按 `projectId` 隔离。
- 后端必须从 token 解析当前用户。
- 前端传入的用户 ID、角色、姓名不能作为可信身份。
- 扫码后也必须由后端解析二维码并校验权限。

## 五、业务流程框架

### 5.1 电箱台账流程

```text
项目安全员进入电箱台账
→ 在 PC 设备巡检后台新增或导入电箱
→ 填写编号、位置、负责电工
→ 生成 `B:<publicCode>` 统一场景码
→ 打印单码贴纸并张贴到现场电箱
```

已确定规则：

- 电箱编号完全自定义，不强制格式；后端统一去首尾空格，限制 1-64 字符，同一项目内唯一。
- `publicCode` 是统一场景码主体；同一码按登录态、项目权限和 `public_access_enabled` 分流内部动作或匿名公开月表，不授予业务权限。
- 历史 `qrCode` 只保留旧客户端和旧数据兼容，当前新贴纸不再生成双码。
- 停用电箱：`status = INACTIVE`，`qrStatus = DISABLED`，不可继续日检，但可查看历史。
- 轮换统一码后旧码写入日志并失效，扫码旧码提示已换绑或停用。
- 拆除电箱：存在未闭环整改时不可拆除；拆除后 `status = REMOVED`、码停用且公开访问关闭，历史巡检记录保留。
- 台账导入：PC 后台下载模板、上传 Excel 预检，存在 `ERROR` 时不提交，`WARN` 可提交；统一码由后端生成。

### 5.2 电工每日巡检流程

```text
电工打开小程序
→ 扫描电箱二维码
→ 进入该电箱日检表
→ 上传外观照片
→ 上传内部照片
→ 填写六项检查结果
→ 六项均正常时直接完成
→ 存在异常时选择合格电工和期限并生成一条整改任务
```

六项检查结果来自原表：

- 内外观
- 漏电保护器
- 熔断
- 保护接零
- 220V 插座
- 380V 插座

当前规则：每项只允许 `NORMAL / ABNORMAL / NA`；异常项说明必填；允许今天及往前 7 天补录；
同一电箱同一天只允许一条有效日检。外观照片和内部照片均为必填且每类至少 1 张。

### 5.3 历史逐条安全复核（当前退出）

```text
电工提交巡检
→ 安全员收到待复核
→ 查看照片和检查项
→ 复核通过 / 退回修改 / 转整改
```

复核结果框架：

| 复核结果 | 后续动作 |
| --- | --- |
| 通过 | 巡检记录归档 |
| 退回 | 电工重新修改提交 |
| 转整改 | 生成整改任务 |

本节只记录历史设计。当前新巡检不生成逐条复核人、复核日志或 `REVIEW` 待办；对应 Controller
映射和正式 Web/小程序入口均退出。安全员当前只复查异常巡检生成的整改任务。

### 5.4 历史安全员现场抽查（当前退出）

```text
安全员现场发现问题
→ 扫描电箱二维码
→ 选择问题分类
→ 上传问题照片
→ 填写问题说明
→ 套用或编辑整改要求模板
→ 指定整改人
→ 默认 3 天整改，可调整整改期限
```

本节只记录历史设计。当前扫码动作不展示安全抽查，也不提交 `SAFETY_SPOT_CHECK`；异常必须在
六项日检内填写说明并由本次日检直接聚合生成整改任务。

### 5.5 整改闭环流程

```text
电工收到整改待办
→ 填写整改说明
→ 上传整改照片
→ 提交安全员复查
→ 安全员/项目管理员复查
→ 关闭整改或退回继续整改
→ 退回后整改人再次提交复查
```

整改状态定义：

- `PENDING`：待整改，整改负责人可填写说明并上传照片。
- `COMPLETED`：待复查，只有具备整改复查权限的管理用户可关闭或退回。
- `REJECTED`：复查退回，记录退回次数和再次提交截止日期，整改负责人可再次提交。
- `CLOSED`：已关闭，整改闭环完成，只读保留历史记录。

规则：

- 整改说明和整改照片后端强制必填。
- 每次提交、关闭、退回都写入整改留痕。
- 退回后 `rejectCount` 累加，`recheckDeadline` 默认按上一次整改/复查截止日期顺延 3 天。
- 关闭、退回和改派仅限当前项目 `SAFETY_OFFICER + inspection.review`；平台管理员保留应急权限。

### 5.6 外部检查扫码查看流程

```text
外部检查 / 公司检查
→ 微信扫描现场电箱二维码
→ 查看该电箱巡检记录汇总
```

已确定规则：

- 允许免登录查看；统一场景码 `B:<publicCode>` 的匿名分支只在公开访问启用时返回脱敏月表。
- 同一统一码的登录内部动作仍须重新校验项目和操作权限；PC 后台可按电箱启用或停用公开访问。
- 公开页只展示项目简称、电箱编号/名称/位置、电箱状态、近 30 天应检/已检/漏检/异常/未闭环数量和最近记录的日期/结果摘要。
- 不展示人员手机号、用户账号、内部用户 ID、照片文件 ID、检查项明细、备注、复核人、复核意见或复核日志。
- `public_access_enabled = 0` 或电箱拆除关闭公开访问后，公开接口返回业务错误，不继续展示历史汇总。

### 7.0 当前五栏正式信息架构

界面统一把 `project_info` 记录显示为“施工区域”，底层仍使用 `projectId` 做数据关联。资料、巡检和质量共享当前施工区域；统一待办默认跨当前用户全部有效项目聚合，并在每条事项中标明所属项目。

V2 交互包含 180ms 页面淡入、220ms 区域底部弹层、指标更新、分段筛选滑动、列表错峰入场、视频交叉淡化、扫码单次扫描线和按钮按压反馈；H5 在减少动效模式下仅保留必要透明度反馈。

| 正式页 | 对应 PC 内容 | 移动端核心内容 |

质量主栏采用“轻量首页 + 独立业务子页”：首页只展示本周周检动态主操作、非零个人质量待办、
待整改/待复查/已逾期三个可跳转指标、最近两条周检和质量资料入口，不再直接铺完整问题列表、
双层筛选和搜索。完整周检记录、整改闭环、问题详情及质量资料分别进入子页；统一待办与周检详情

资料详情的当前版本和历史版本使用同一文件操作流程：点击“下载”后先显示目标文件名和版本，并提供“打开保存菜单”和“发送给微信好友”。PDF、Word、Excel、PowerPoint 使用微信 `openDocument({ showMenu: true, fileType })` 打开原生文档菜单；具体可保存位置和其他应用选项由手机系统与微信客户端决定。`.md`、`.txt`、压缩包等不受 `openDocument` 支持的格式不得伪装扩展名或自动转换，选择保存时应明确提示限制，并保留“发送给微信好友”入口。

任意格式都应使用下载后的临时文件和版本原始文件名调用 `wx.shareFileMessage`，不得丢失 `.md`、`.pdf` 等扩展名；基础库低于 2.16.1 时提示升级微信。下载期间禁止重复触发，用户取消原生菜单或好友选择时静默返回。小程序不再使用 `uni.saveFile` 保存到内部沙箱，也不再显示无法指明真实位置的“文件已保存”提示；H5 和 PC Web 的既有下载行为保持不变。正式微信预览和上线环境必须将后端 HTTPS 域名配置为 `downloadFile` 合法域名。

原生操作成功后，小程序调用 `POST /api/v1/project-documents/{id}/client-actions`，以 `OPEN_SAVE_MENU` 或 `SHARE_WECHAT_FILE` 和目标 `versionId` 记录最终动作；取消、格式不支持或失败时不调用。下载记录与最终动作记录分别保留，不增加资料表或版本表字段。

PC Web 端在一级“巡检管理”模块中承担后台管理职责，与小程序现场端共用同一套电箱、检查、整改、附件和权限数据。

| 页面/页签 | 主要用户 | 核心内容 |
| --- | --- | --- |
| 电箱台账 | 平台管理员 / 项目管理员 / 安全员 | 电箱新增编辑、台账导入、二维码贴纸、公开只读启停、停用/拆除和负责人维护 |
| 巡检记录 | 项目有效成员 | 查看正常、整改中和已闭环巡检详情，按项目、电箱、月份或日期统计并导出 |
| 整改闭环 | 平台管理员 / 项目安全员 / 整改负责人 | 查看整改任务；负责人提交整改，安全员复查关闭/退回或改派 |
| 系统管理授权 | 平台管理员 | 维护项目角色、巡检菜单和 `inspection.*` 操作权限 |

## 八、数据框架

### 8.2 派生数据

小程序不建立本地待办业务表。巡检与质量待办由后端按业务状态实时派生，用印审批任务持久化在统一审批表，抄送和通知分别由统一抄送、通知表提供；项目巡检统计、电箱今日状态和公开只读汇总仍由后端实时派生。

| 派生数据 | 来源 | 说明 |
| --- | --- | --- |
| 项目统计 | `project_info`、`electric_box`、`inspection_record`、`inspection_rectification` | 小程序项目列表和工作台展示电箱数、今日巡检、今日待检和待整改等；不再展示历史逐条待复核指标 |
| 电箱今日状态 | `electric_box`、`inspection_record`、`inspection_rectification` | 展示已检、未检、异常、停用、未闭环整改等状态 |
| 统一待办 | 巡检、质量业务表，`workflow_approval_task`、`workflow_cc_recipient`、`user_notification` | 后端按当前 token 用户聚合“待我处理 / 抄送我的 / 通知”，返回稳定事项键和受控路由 |
| 巡检汇总 | `inspection_record`、`inspection_record_item`、`inspection_rectification` | 项目或单箱按月统计应检、已检、漏检、异常、未闭环 |
| 公开汇总 | `electric_box`、`inspection_record`、`inspection_rectification` | 外部只读页只返回脱敏字段，不返回内部 ID、账号、手机号或照片 ID |

### 8.3 数据原则

- 所有业务数据必须按 `projectId` 隔离。
- 后端必须从 token 解析当前用户，前端传入的用户 ID、角色、姓名不能作为可信身份。
- 小程序不保存本地待办；巡检、质量事项实时派生，用印审批、抄送和通知由服务端统一工作流及通知表持久化并聚合返回。
- 文件附件继续复用 `file_resource`，通过 `businessType` 和 `businessId` 关联人员证件、质量周检现场/问题草稿、质量问题/整改/复查/资料、检查记录或安全整改任务。已绑定周检草稿照片长期保留到提交或人工放弃，不受 24 小时未绑定暂存清理影响。

## 九、接口框架

接口详情以 `docs/接口规则.md` 为准。本章按小程序和 PC 巡检后台共用的业务能力分组，确保页面、接口和数据对象能互相对应。

| 分组 | 关键能力 | 代表接口 |
| --- | --- | --- |
| 登录与用户信息 | 账号密码登录；获取当前用户；登出；返回全局角色和项目职责 | `POST /api/v1/auth/login`<br>`GET /api/v1/auth/user-info`<br>`POST /api/v1/auth/logout` |

| 人员与教育 | 公共汇总；人员台账；进退场；证件；指定人员教育 | `/api/v1/personnel/summary`<br>`/api/v1/personnel/{id}/entry`<br>`/api/v1/personnel/{id}/movements`<br>`/api/v1/personnel/certificates`<br>`/api/v1/safety-education` |

| 整改闭环 | 整改列表；详情；电工完成整改；安全员关闭、退回和改派 | `/api/v1/inspection/rectifications`<br>`/api/v1/inspection/rectifications/{id}/complete`<br>`/api/v1/inspection/rectifications/{id}/assign`<br>`/api/v1/inspection/rectifications/{id}/close`<br>`/api/v1/inspection/rectifications/{id}/reject` |
| 统一待办与通知 | 聚合巡检、质量、用印的待处理/抄送事项，提供汇总、通知列表和已读操作 | `GET /api/v1/me/todos?scope=PENDING|CC`<br>`GET /api/v1/me/work-summary`<br>`GET /api/v1/me/inbox` |

接口调用原则：

- 小程序真实模式下默认走后端接口；只有显式设置 `VITE_USE_MOCK=true` 才使用离线演示数据。
- 所有需要登录的接口都必须携带 `Authorization: Bearer <token>`。
- 前端只能传业务参数，身份和权限以后端 token 解析结果为准。
- 带 `projectId`、`electricBoxId`、检查记录 ID 或整改任务 ID 的接口必须由后端反查项目并校验权限。

## 十、通知与待办框架

首版只实现小程序内待办、抄送和站内通知，不依赖微信订阅消息、短信或企业微信通知完成闭环。

### 10.1 统一个人工作台

待办不再固定为巡检四类。页面先按个人收件范围分为“待我处理 / 抄送我的 / 通知”，再按“巡检 / 质量 / 用印”业务分类筛选：

| 收件范围 | 数据来源 | 操作口径 | 点击后进入 |
| --- | --- | --- | --- |
| 待我处理 | 巡检、质量实时派生事项；持久化的用印审批任务 | 仅返回当前用户有权处理的事项 | 服务端 `routeCode + routeParams` 指定的受控页面 |
| 抄送我的 | 统一业务抄送关系 | 只读查看，不产生审批或整改权限 | 对应业务详情 |
| 通知 | `user_notification` | 支持单条已读、全部已读和未读角标 | 对应业务详情 |

说明：

- 巡检兼容类型 `INSPECTION / REVIEW / RECTIFICATION / RECHECK` 只描述巡检业务动作，不再限定统一待办的全部类型；用印审批使用 `SEAL_APPROVAL`，质量事项由质量业务来源识别。
- 每条事项使用稳定字符串 `todoKey` 去重和渲染；小程序优先消费服务端 `routeCode + routeParams` 导航，不再依赖临时数字 ID 或按 `businessType` 硬编码跳转。
- 业务资格与可操作性均由后端按当前 token、项目成员状态和具体任务校验，抄送人只有查看权限。

### 10.2 微信通知

- 微信订阅消息为后续增强项，首版不实现。
- 订阅消息不能替代站内待办；即使后续接入通知，业务闭环仍以接口状态和站内待办为准。
- 后续如实现微信订阅消息，需要补充订阅消息模板、用户订阅状态、发送记录、失败重试和退订处理。

### 10.3 其它通知

- 短信、企业微信、邮件等通知暂不纳入首版。
- PC 后台的整改提醒/逾期升级当前是业务留痕和状态提示，不等同于外部消息推送。

## 十一、验收框架

首版验收先按业务闭环验证。

| 场景 | 验收目标 |
| --- | --- |
| 电箱台账 | 能明确项目有多少电箱需要巡检 |
| 一箱一码 | 扫码能进入正确电箱 |
| 电工日检 | 外观、内部照片各上传至少 1 张后才能提交检查表 |
| 正常/异常分支 | 正常巡检直接完成；异常巡检只生成一条整改任务且不生成历史逐条复核 |
| 历史入口退出 | 项目工作台、扫码结果和正式路由均不显示逐条安全复核或安全抽查 |
| 整改闭环 | 被指派电工能反馈，项目安全员能关闭、退回或改派 |
| 待办提醒 | 登录用户能看到跨授权项目的待处理、抄送和站内通知，并进入正确业务详情 |
| 汇总查看 | 单个电箱能查看巡检记录汇总 |
| 月度导出 | 能按月还原原检查表字段 |
| 权限隔离 | 用户不能访问未授权项目数据 |

## 十二、待确认问题

这些问题后续需要项目方确认后再细化：

1. 外部检查扫码查看巡检汇总是否允许免登录。
2. 免登录查看时展示哪些字段，是否隐藏人员信息。
3. 电箱编号规则由项目统一制定，还是系统自动生成。
4. 二维码由系统生成后打印，还是支持导入已有二维码。
5. 电工是否必须是系统用户。
6. 一个电箱是否只有一个负责电工，是否需要备用电工。
7. 安全员复核是否必须每日完成。
8. 电工是否允许补录，允许补录几天。
9. 整改默认 3 天是否所有问题都适用。
10. 月度导出最终使用 Excel、Word 还是两者都需要。
