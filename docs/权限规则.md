# 权限规则

## 2026-08-03 角色、菜单与操作权限分层（当前口径）

角色基本信息、菜单可见性和页面内操作权限分别保存。编辑角色名称、说明或状态时，
未传授权字段必须保留已有 `sys_role_menu`、`sys_role_permission` 和
`sys_role_business_module`，不得因基本信息编辑清空授权。新建自定义角色固定为
`PROJECT`；`PLATFORM_ADMIN` 只由受保护运维流程管理，不在业务页授予。
自定义角色编码由服务端自动生成并在创建后保持不变，管理员只填写名称、说明和状态；
已有固定编码以及旧客户端显式提交的合法编码继续兼容。

三个业务模块仍为 Web/小程序共用开关；页签菜单只细分 Web 可见页面：

- 资料管理：`DOCUMENT_LIBRARY`、`DOCUMENT_RECYCLE`。
- 巡检管理：`INSPECTION_LEDGER`、`INSPECTION_RECORDS`。
- 质量管理：`QUALITY_ISSUES`、`QUALITY_DOCUMENTS`。
- 系统管理：仍使用 `SYSTEM_REGISTRATION / SYSTEM_USER / SYSTEM_ROLE /
  SYSTEM_MENU / SYSTEM_PROJECT / SYSTEM_WECHAT / SYSTEM_AUDIT`。

取消父菜单必须取消子页签；取消页签时，服务端在同一事务内清理已不属于任何已选菜单的
操作权限。操作权限单独保存时不改变菜单。所有授权变更都要清理项目权限缓存、注销受影响账号
全部会话并写操作日志。

巡检管理界面不直接展示技术性前置权限，由服务端统一补齐：

| 管理员可见动作 | 实际权限组合 |
| --- | --- |
| 查看电箱台账 | `inspection.view + BOX_VIEW` |
| 管理电箱台账 | 查看台账 + `inspection.manage + BOX_MANAGE` |
| 二维码 / 公开访问 | 查看台账 + `BOX_QR_MANAGE` / `BOX_PUBLIC_ACCESS` |
| 提交日检 | `inspection.submit + INSPECTION_DAILY_SUBMIT` |
| 查看记录 | `inspection.view + INSPECTION_RECORD_VIEW` |
| 查看汇总 | `inspection.view + SUMMARY_VIEW` |
| 导出汇总 | 查看汇总 + `inspection.export + SUMMARY_EXPORT` |

同一用户在同一项目的多角色继续按并集生效，不增加用户级 `permissionIds[]`。资料、巡检、
质量页面只展示当前项目角色并集中的页签；原页签失权后自动回退到首个可访问页签。迁移前只有
父菜单且当前模块完全没有页签记录时，前端临时按旧逻辑显示该模块全部页签。

## 2026-07-29 跨端业务模块统一开关（当前口径）

资料、巡检、质量是三项**业务模块**，不是两套分别授权的 Web / 小程序菜单。角色配置页只展示一次“资料管理 / 巡检管理 / 质量管理”：关闭任一模块会同步移除该角色的 `WEB_*` 与 `MINI_*` 两个入口；重新打开时恢复这两个入口。细分操作权限（例如上传资料、提交巡检、质量复查）仍独立勾选，模块关闭期间保留配置但不生效，重新启用后按原细分权限继续生效。

模块开关保存在 `sys_role_business_module`，有效模块按当前项目的多个角色并集计算。`/auth/user-info` 针对每个项目返回过滤后的 `menuCodes[]`、有效权限码；Web 顶部导航、小程序自定义导航、页面守卫均以此隐藏入口。`BusinessModulePermissionInterceptor`、资料/质量服务和巡检旧兼容权限服务继续在后端按目标项目检查模块，模块关闭后直接访问接口也返回 HTTP `403`。`PLATFORM_ADMIN` 不再绕过这三项业务模块开关，但仍保有独立的平台系统管理权限。

巡检、质量的通用附件也属于原业务模块：通过 `/files` 直接读取、下载、预览或按 `businessType` 列表查询时，仍要按附件真实项目检查对应模块，不能借通用文件通道绕过开关。

因此，关闭某一个角色的资料模块，只会撤销该角色的资料贡献；同一用户在该项目若仍有另一角色启用了资料，按多角色并集规则资料仍然可见和可用。若目标是让某用户看不见资料，需要在该用户当前项目的所有角色中都取消资料模块，或移除会继续授予资料的角色。

系统管理菜单（注册审核、用户、角色、菜单、项目成员、微信、审计）不属于业务模块，保持 Web 平台管理目录，不与小程序“我的”合并。原始 `WEB_* / MINI_*` 菜单记录仅用于各客户端路由兼容；日常角色配置不应分别编辑它们。

## 2026-07-30 质量细分操作权限（当前口径）

质量动作统一按目标项目的细分权限判断，不再把 `PROJECT_ADMIN`、`SAFETY_ADMIN`
或其他固定角色编码作为附加门槛。普通项目角色只要在目标项目具有 `ACTIVE` 成员关系、
启用了 `QUALITY` 模块并取得相应权限码，就可以执行对应动作：

| 动作 | 权限规则 |
| --- | --- |
| 查看问题、统计、详情和当前项目质量资料 | `quality.view` |
| 发起问题、改派、调整整体闭环期限、作废以及管理 `QUALITY_DOCUMENT` | `quality.manage` |
| 提交整改 | 必须有 `quality.rectify`，且为当前被指派人或同时有 `quality.manage` 可管理代办 |
| 复查通过或退回 | `quality.review`，不再额外要求 `quality.manage` 或固定管理角色 |

菜单和按钮仍只用于前端体验；后端必须按业务记录真实 `projectId` 重新校验上述项目范围、
模块和权限。拥有某个角色名称本身不直接获得质量动作权限，同一项目多个角色的模块和
权限继续按并集计算。

## 2026-07-29 项目级多角色与项目经理成员管理（当前口径）

本节取代下方旧的“巡检权限角色模板”口径。权限不再由模板参与计算，而是由**平台管理员资格、当前项目的多个项目角色、角色菜单、角色操作权限和项目访问状态**共同决定。

| 层级 | 规则 |
| --- | --- |
| 平台级 | 仅受保护的 `PLATFORM_ADMIN` 可以使用注册审核、全量用户、角色与权限、菜单与功能、微信绑定、操作日志及跨项目管理。该全局身份不作为普通业务角色，不在“用户管理”页展示或分配。 |
| 项目级 | 所有业务角色均为 `PROJECT` 角色；系统管理员预先创建、启停并配置资料、巡检、质量菜单和操作权限。不得对单个用户单独加减权限。 |
| 多角色 | 同一用户在同一项目可拥有多个角色，`sys_user_project_role` 以 `project_id + user_id + role_id` 唯一保存，菜单与操作权限取并集。 |
| 范围 | `sys_user_project.status=ACTIVE` 是项目访问前提；暂停成员保留角色，恢复后继续按原角色生效。 |

`PROJECT_ADMIN` 正式显示为“项目经理”，是受保护项目角色：系统管理员可配置其三大模块权限，但只有系统管理员可授予、撤销或调整该角色。仅项目经理角色可以拥有 `project.member.manage`；任何自定义项目角色都不能获得该权限。

角色分配发生在注册审核、用户管理和项目成员管理。用户管理使用“项目 → 角色”树，项目成员管理使用“用户 → 角色”树；父节点表示成员关系而不是全选子角色。首次勾选父节点自动选择启用中的内置 `USER`，取消最后一个角色转为待移出，所有勾选在“保存全部”后通过批量事务提交。用户表格直接展示最多两个“项目 + 角色”摘要及 `+N`，不必进入详情才能判断主要授权。`roleIds[]` 仅为传输字段，不增加用户级直接权限。

项目经理只可在自己当前项目内：搜索并加入已启用的既有系统账号、移出普通成员、调整普通成员的非项目经理角色、暂停或恢复普通成员访问。项目经理角色节点、拥有项目经理角色的成员及本人均只读；候选接口只返回姓名、账号、当前项目关系和当前项目角色，不返回手机号、邮箱或其他项目关系。平台管理员可通过用户树跨项目批量配置。批量写入先完整校验再落库，任一成员受质量未闭环、电箱责任、待整改或保护规则阻止时整批回滚；暂停/恢复独立提交，角色调整不隐式恢复访问。

`GET /api/v1/auth/user-info` 对每个项目返回 `projectRoles[]`、有效菜单和有效权限码；Web、小程序页面守卫和首个可访问页面必须以当前项目上下文为准。前端隐藏不是安全边界，后端按权限码与目标 `projectId` 返回 HTTP `403`。

巡检模板表、模板字段和旧接口仅保留历史兼容；其旧接口已返回 `410`，不再创建、编辑、分配或参与鉴权。历史模板权限已在迁移中并入对应项目角色；自定义历史模板会生成可追溯的迁移项目角色。

## 2026-07-28 通用 RBAC 与项目范围（历史说明）

当前权限模型由“平台角色 + 项目角色 + 菜单 + 操作权限 + 项目数据范围”共同决定，不增加用户级权限覆盖：

| 层级 | 存储/返回 | 作用 |
| --- | --- | --- |
| 平台角色 | `sys_user_role`、`sys_role.scope_type=PLATFORM` | 决定跨项目平台能力；`PLATFORM_ADMIN` 拥有当前正式权限目录的全部权限 |
| 项目角色 | `sys_user_project.project_role_code`、`sys_role.scope_type=PROJECT` | 只在有效项目成员关系范围内生效，兼容既有项目职责和巡检权限模板 |
| 菜单 | `sys_menu`、`sys_role_menu` | 控制 Web/小程序可见入口和登录后的首个落点 |
| 操作权限 | `sys_permission`、`sys_role_permission` | 控制按钮和后端接口动作 |
| 项目范围 | `sys_user_project.status=ACTIVE` | 限定具体项目数据；角色有权限码但不在项目范围内时仍不得访问 |

`GET /api/v1/auth/user-info` 返回 `menus`、平台 `permissionCodes`、`projectRoles/projectContexts` 及各项目权限码。Web 和小程序据此隐藏菜单与操作并回落到第一个有权页面；小程序自定义底部导航和页面守卫也使用同一结果。前端判断不是安全边界，后端 `BusinessModulePermissionInterceptor` 与各业务服务必须继续校验操作权限和项目范围，无权访问返回真实 HTTP `403`。

当前菜单目录：

- Web 正式业务：`WEB_DOCUMENT`、`WEB_INSPECTION`、`WEB_QUALITY`。
- 系统管理：`WEB_SYSTEM`，子菜单为 `SYSTEM_REGISTRATION`、`SYSTEM_USER`、`SYSTEM_ROLE`、`SYSTEM_MENU`、`SYSTEM_PROJECT`、`SYSTEM_WECHAT`、`SYSTEM_AUDIT`。
- 小程序保持资料、巡检、质量、我的四个一级入口；前三项按菜单/权限聚合显示，“我的”作为当前用户入口保留。

当前通用操作权限：

| 模块 | 权限码 |
| --- | --- |
| 注册审核 | `system.registration.review` |
| 用户 | `system.user.view`、`system.user.manage`、`system.user.status`、`system.user.reset_password` |
| 角色/菜单 | `system.role.manage`、`system.menu.manage` |
| 项目/微信/审计 | `project.member.manage`、`system.wechat.manage`、`system.audit.view` |
| 资料 | `document.view`、`document.upload`、`document.manage` |
| 巡检 | `inspection.view`、`inspection.submit`、`inspection.manage`、`inspection.export` |
| 质量 | `quality.view`、`quality.manage`、`quality.rectify`、`quality.review` |

平台管理员可查看完整系统管理；其受保护的全局身份由初始化或受保护运维机制维护，不在业务界面授予。项目管理员只可在已授权项目内管理成员、项目角色和已有用户的项目访问申请，不能审核新账号、处理平台权限或管理其他项目。普通用户只能获得其角色菜单、操作权限和有效项目范围；直接请求未授权接口返回 HTTP `403`。

微信绑定同样属于权限边界：同一 AppID 下有效的系统用户、OpenID、UnionID 一对一；不能因手机号相同自动绑定。自助解绑只允许已启用密码登录的用户重新验证密码，解绑后注销全部会话；仅微信登录账号由平台管理员处理。

本期只保护并展示当前正式资料、巡检、质量和系统管理目录；地图、人员、摄像头、设备等隐藏旧功能不恢复、不进入本期权限目录。巡检模板不再参与项目权限计算，旧字段只保留历史兼容。

上述结构依赖唯一增量迁移 `20260728_unified_registration_rbac_wechat_login.sql`。已在副本连续演练并于 2026-07-29 应用到当前本地库；管理员停用菜单或撤销角色关联后重跑不会恢复授权。禁止执行 `init.sql`。正式微信权限链路仍需正式 AppID/AppSecret、合法 HTTPS 域名和真机验收。

## 权限总体原则

系统是多项目平台，权限必须同时考虑：

1. 用户是否登录。
2. 用户拥有什么角色。
3. 用户是否有当前 `projectId` 的访问或管理权限。
4. 操作是查看、新增、编辑、删除，还是项目级管理动作。

特别注意：

- 涉及当前登录用户的数据，必须以后端登录态为准。
- 后端不能信任前端传入的 `userId`、`username`、`role`。
- 前端权限只能作为体验优化，不能作为安全边界。
- 所有带 `projectId` 的后端接口都应该校验当前用户项目权限。

## 三模块跨端权限补充（2026-07-19）

- Web 与小程序只负责按后端返回结果隐藏或展示操作，不能形成不同的权限边界。
- 工程资料版本文件属于 `PROJECT_DOCUMENT` 保留类型，只能经资料接口访问；通用文件接口不得绕过资料上传人、版本、归档和回收站规则。
- 巡检和质量暂存附件绑定时必须同时校验当前 JWT 用户是上传人、文件与业务记录属于同一项目、暂存业务类型匹配且尚未绑定。
- 已绑定流程附件不能经通用文件接口修改或删除；需要更换附件时必须走对应业务流程，避免 Web 修改后小程序仍引用失效文件 ID。
- 普通项目成员不显示资料目录管理和回收站入口，但真正的目录、恢复和永久删除权限仍由后端 `canManage` 规则校验。

## 电箱巡检权限模板（历史兼容，已停用）

> Web 界面为降低理解成本，将“权限模板”统一显示为“权限角色”。后端实体、字段、接口路径和数据库表仍沿用 `permissionTemplate` / `inspection_permission_template`，两者指向同一套授权能力。

> 当前唯一维护入口为 Web「系统管理 > 角色与权限 > 巡检权限角色模板」；具体项目成员的模板分配在「系统管理 > 项目授权」。`sys_role` 通用角色负责菜单和通用操作权限，巡检权限角色模板负责项目内电箱、巡检、记录和汇总等细分权限，两者同时生效但不是同一张表。

> 2026-07-11 极简版：正式权限目录只展示台账、巡检提交、记录查看、汇总导出和项目授权。`INSPECTION_REVIEW`、`RECTIFICATION_VIEW`、`RECTIFICATION_REVIEW` 常量仅为读取旧模板/历史数据保留，不再出现在权限配置目录，也不能触发复核或整改入口。

电箱巡检已从固定项目职责下拉升级为“权限模板 + 项目用户授权”的组合模型：

- 全局 `PLATFORM_ADMIN` 仍代表平台管理员，可维护全局权限模板，并默认拥有全部电箱巡检权限。
- 不新增全局 `ELECTRICIAN` 角色。
- 巡检员身份不放在 `sys_role`，以当前项目 `INSPECTION_DAILY_SUBMIT` 权限判断；不再要求必须是电箱负责人。
- 同一用户可以在 A 项目绑定“安全管理员”模板，在 B 项目绑定“项目成员/负责电工”模板。
- 项目内绑定关系保存在 `sys_user_project.inspection_permission_template_id`。
- `sys_user_project.project_role_code` 暂时保留，用于旧数据迁移、项目职责展示和非巡检模块兼容。

| `INSPECTION_REVIEW` | 历史兼容权限码，当前产品不使用 |
| `INSPECTION_RECORD_VIEW` | 查看项目检查记录 |
| `RECTIFICATION_VIEW` | 历史兼容权限码，当前产品不使用 |
| `RECTIFICATION_REVIEW` | 历史兼容权限码，当前产品不使用 |
| `SUMMARY_VIEW` | 查看巡检汇总 |
| `SUMMARY_EXPORT` | 导出巡检汇总 Excel |
| `PERMISSION_MANAGE` | 项目用户授权和权限模板分配 |

后端核心规则：

- 所有带 `projectId` 的巡检接口必须以后端 token 解析出的用户为准。
- 前端传入的用户 ID、角色、姓名不能作为可信身份。
- `ProjectPermissionService.hasInspectionPermission(userId, projectId, permissionCode)` 是电箱巡检业务权限判断入口。
- `ProjectPermissionService.canManageInspection(userId, projectId)` 仅作为兼容方法，内部已映射到权限码判断。
- `ProjectPermissionService.canManageProjectMembers(userId, projectId)` 已映射到 `PERMISSION_MANAGE`。
- 所有项目权限查询同时要求 `sys_user_project.status=ACTIVE`；暂停成员保留职责和模板，但任何项目权限立即失效。
- 设置电箱负责巡检员时，如该用户未加入项目，后端自动补一条 `USER` 项目授权。
- 设置电箱安全负责人时，如该用户未加入项目，后端自动补一条 `SAFETY_ADMIN` 项目授权。
- 电箱新增、编辑、停用、拆除和导入走 `BOX_MANAGE`。
- 二维码换绑、补打、贴纸和日志走 `BOX_QR_MANAGE`。
- 公开扫码启停走 `BOX_PUBLIC_ACCESS`。
- 普通编辑不得修改电箱所属项目、`status` 或 `qrStatus`；如果编辑请求同时改变
  `qrCode` 或 `publicAccessEnabled`，除 `BOX_MANAGE` 外还必须追加
  `BOX_QR_MANAGE` 或 `BOX_PUBLIC_ACCESS`，不能借普通编辑绕过细分权限。
- 传入负责电工或安全负责人用户 ID 时，后端必须确认其为启用账号并使用服务端姓名；
  无效账号必须在电箱写入及项目成员自动补授权前拒绝。
- 安全复核走 `INSPECTION_REVIEW`；整改关闭/退回走 `RECTIFICATION_REVIEW`；汇总查看和导出分别走 `SUMMARY_VIEW`、`SUMMARY_EXPORT`。
- 电箱拆除前后端均会阻止未闭环整改电箱被拆除；拆除后内部码停用、公开访问关闭，但历史记录仍可查看。
- 换绑、停用、拆除后的旧内部二维码编码写入 `electric_box_qr_log`，后端解析旧码时返回已换绑或停用提示，不允许再次绑定。
- 外部检查人员不进入账号体系，使用 `publicCode` 访问脱敏只读汇总，并受 `electric_box.public_access_enabled` 控制。
- 统一扫码调用者没有目标项目巡检权限且 `public_access_enabled=0` 时，后端返回 HTTP
  `403`，不返回电箱编号、名称、位置等元数据，也不查询巡检范围或当天内部记录。

## 电箱检查权限规则

当前已实现于：

- `backend/src/main/java/com/example/siteplatform/electricbox/service/ElectricBoxService.java`

### 电箱台账

- 查看：登录用户必须拥有电箱所属项目权限。
- 普通用户列表、详情和内部扫码解析只返回/允许自己负责的电箱。
- 新增、编辑、停用：`PLATFORM_ADMIN`，或授权项目内 `PROJECT_ADMIN` / `SAFETY_ADMIN`。
- 内部扫码解析：先解析 `qrCode`，再校验电箱所属项目权限。

### 电箱日检

- `PLATFORM_ADMIN` 可在全部项目提交和查看。
- 授权项目内 `PROJECT_ADMIN` / `SAFETY_ADMIN` 可提交和查看。
- 拥有 `INSPECTION_DAILY_SUBMIT` 的项目成员可巡检当前项目任意启用且处于巡检范围内的电箱，不再校验电箱负责人关系。
- 拥有 `INSPECTION_DAILY_SUBMIT` 的项目成员可查看当前项目全部电箱巡检记录，保证页面与完整单箱月表一致。
- 单箱月表或单箱日期范围报表允许 `INSPECTION_DAILY_SUBMIT` 或 `SUMMARY_EXPORT`；多个电箱、全部电箱及项目级导出只允许 `SUMMARY_EXPORT`。
- 后端从 token 写入 `inspector_id`、`inspector_name`，不信任前端传入检查人。

### 安全复核

- 电工提交巡检后默认 24 小时内完成复核，后端写入 `inspection_record.review_due_time`。
- 多安全员分配规则：优先分配给电箱 `safety_manager_id`；没有安全负责人时，进入项目内拥有 `INSPECTION_REVIEW` 权限用户可见的未分配共享池。
- `POST /api/v1/inspection/records/{id}/review` 允许 `PLATFORM_ADMIN`、授权项目 `PROJECT_ADMIN`、授权项目 `SAFETY_ADMIN` 或拥有 `INSPECTION_REVIEW` 权限模板的项目成员。
- 已分配给具体安全员的记录，只允许该安全员复核；项目管理员、平台管理员或拥有 `PERMISSION_MANAGE` 的用户可处理和改派。
- `POST /api/v1/inspection/records/{id}/assign-reviewer` 仅允许平台管理员、项目管理员或拥有 `PERMISSION_MANAGE` 的项目成员。
- 复核通过、退回、转整改、自动分配、改派、取消分配和逾期标记都会写入 `inspection_review_log`。
- `REJECT` 和 `RECTIFY` 必须填写复核意见；前端不能绕过，后端仍会校验。
- 复核通过后归档；退回后记录进入退回状态；转整改时创建整改任务。
- 转整改可指定问题分类、整改人和整改期限；整改人必须拥有当前项目权限，整改期限不能早于当天。

### 整改闭环

- 整改完成：整改责任人本人，或有 `RECTIFICATION_REVIEW` 权限的管理用户。
- 整改列表/详情中，普通用户只能查看分配给自己的整改任务。
- 关闭/退回整改：仅 `PLATFORM_ADMIN`，或授权项目内具备 `RECTIFICATION_REVIEW` 权限的 `PROJECT_ADMIN` / `SAFETY_ADMIN` 等管理用户。
- 改派整改人、调整整改期限、跟进提醒和逾期升级提醒：仅具备 `RECTIFICATION_REVIEW` 权限的管理用户。
- 安全抽查发起整改：需要 `INSPECTION_REVIEW` 权限；前端可选择问题分类、模板、整改人和期限，后端仍按 token 和项目权限校验。
- 关闭整改后，如果该检查记录下没有未关闭整改，检查记录状态置为 `CLOSED`。

### 公开扫码只读

- `GET /api/v1/public/electric-boxes/{publicCode}/summary` 无需登录。
- 只返回项目简称、电箱编号/名称/位置、状态、近 30 天巡检统计和最近记录。
- 不返回手机号、账号、内部用户 ID，也不提供写操作。

## 后端权限校验规则

新增或修改接口时必须遵守：

### 读取列表

带 `projectId` 的列表接口：

```text
1. 从 token 获取 currentUser
2. 如果 projectId 为空：
   - 平台管理员可查所有，或按业务要求必须传 projectId
   - 非平台管理员只能查有权限项目的数据
3. 如果 projectId 不为空：
   - 调用 checkProjectPermission(currentUser.id, projectId)
4. 查询时加 project_id 条件
```

### 读取详情

详情接口如果只有 `id`，必须先查出记录，再根据记录的 `projectId` 校验权限。

不能只校验登录态。

### 新增数据

新增人员、培训、文件、摄像头、设备时：

```text
1. 从 token 获取 currentUser
2. 从请求体或表单拿 projectId
3. 校验 currentUser 是否能管理该 projectId
4. uploaderId、creatorId 等用户字段以后端 currentUser 为准
```

### 更新和删除

更新/删除时：

```text
1. 从 token 获取 currentUser
2. 根据路径 id 查询现有记录
3. 从现有记录取 projectId
4. 校验当前用户是否有该项目管理权限
5. 执行更新或删除
```

不能信任请求体里的 `projectId`。

### 文件下载

下载文件时：

```text
1. 查询 file_resource
2. 取 file.projectId
3. 校验当前用户项目权限
4. 再返回物理文件
```

当前文件详情、下载、更新、状态更新和删除均已执行第 3 步；修改和删除还需满足平台管理员、上传者或对应项目管理身份之一。

### 工程资料库

- 授权项目成员：列表、详情、预览、下载、上传 V1。
- 资料上传人：可修改本人 `ACTIVE` 资料、移动、上传新版本、归档和移入回收站。
- 平台管理员、授权项目 `PROJECT_ADMIN`：目录 CRUD、管理项目全部资料、恢复归档、查看回收站、恢复和永久删除。
- `ARCHIVED` 资料只允许查看和下载，不允许修改属性、移动或上传新版本。
- Web 与小程序使用同一权限结果；小程序统计接口的 `canManage` 只控制目录和回收站入口显示，不能替代后端写操作校验。
- 目录和资料接口均以后端 JWT 用户为准；不得信任前端传入的用户、角色或上传人字段。
- 永久删除先校验管理员和项目归属，再清理全部版本物理文件、`file_resource`、版本和资料主记录。

### 人员隐私与附件

- 平台管理员、授权项目 `PROJECT_ADMIN` / `SAFETY_ADMIN` 可读取完整手机号和身份证号。
- 普通项目成员只返回脱敏手机号和身份证号，不能通过列表或详情绕过。
- 人员进退场、证件维护和教育完成必须由后端校验项目管理权限。
- 证件附件与人员必须属于同一项目，操作人从 token 获取。

### 质量闭环与附件

- 所有质量动作都要求目标项目 `ACTIVE` 访问和 `QUALITY` 模块；普通项目角色可按细分
  权限执行，不再附加 `PROJECT_ADMIN` / `SAFETY_ADMIN` 固定角色白名单。
- `quality.manage` 控制问题创建、改派、整体闭环期限调整、作废和
  `QUALITY_DOCUMENT` 管理；作废原因必须留痕。
- 质量整改人通过专用只读接口选择，不复用项目成员管理接口；候选账号必须启用、项目访问有效、质量模块可见，并同时具备 `quality.view` 和 `quality.rectify`。
- 平台管理员也必须满足目标项目有效范围、`QUALITY` 模块、`quality.view` 和
  `quality.rectify`，不能凭平台角色绕过整改人候选条件。
- 创建问题和后续改派复用同一后端资格校验，前端传入任意用户 ID 不能绕过。
- 提交整改必须具备 `quality.rectify`，并且是当前被指派人；同时具备
  `quality.manage` 时可不受当前指派限制进行管理代办。`quality.manage` 单独不能提交
  整改，也不能据此获得复查能力。
- `quality.review` 独立控制复查通过和退回，不再要求同时具备 `quality.manage` 或固定
  管理角色。
- 当前不强制发起人、整改人和复查人三者分离；同一账号只有在目标项目分别具备对应管理、整改、复查权限时才能代办相应环节，所有动作仍按 JWT 操作人逐条留痕。
- 成员仍有 `PENDING / RECHECK` 质量整改时不能移出项目或暂停访问；调整角色也不能撤销其质量模块、查看或整改权限，必须先改派、关闭或作废。`CLOSED / VOIDED` 不属于未闭环任务。
- 问题照片、整改照片、复查附件和质量资料均通过 `file_resource` 复用，绑定时校验同项目归属。
- `QUALITY_DOCUMENT` 是由目标项目具备 `quality.manage` 的人员在 PC 端人工维护的项目级质量资料；小程序只读当前项目 `ACTIVE` 资料。它不是检查、整改或复查自动生成的附件，也不属于工程资料库。
- 已关闭和已作废质量问题只读；逾期由
  `status in (PENDING, RECHECK) + deadline < today` 实时计算，`VOIDED`
  不计入逾期或闭环率分母。

### 小程序电箱台账和现场检查

统一场景码 `B:<publicCode>` 只负责定位电箱，不授予权限。所有写操作必须同时校验登录 token、`ACTIVE` 项目授权、巡检权限、电箱状态和检查日期是否处于巡检范围。拥有 `INSPECTION_DAILY_SUBMIT` 的用户可巡检当前项目任意符合条件的电箱；未登录、无项目权限或项目访问被暂停的用户仅在 `public_access_enabled=1` 时查看公开月表。

### 微信绑定与小程序注册用户管理

- `sys_user_wechat_binding.status=ACTIVE` 才能通过微信换取系统 token。
- `DISABLED` 表示平台管理员锁定，不能通过手机号授权自行恢复；只有平台管理员可恢复。
- `UNBOUND` 表示已解绑；密码登录可用的账号可在重新验证账号密码和新的微信 code 后再次绑定。
- 同一 AppID 下，有效的系统用户、OpenID、UnionID 均保持一对一。
- 新用户只能通过统一注册申请创建，不再创建微信专用随机账号。历史 `password_login_enabled=0` 账号不能使用密码登录，其解绑和凭证恢复只能由平台管理员处理。
- 统一账号注册只允许拥有 `system.registration.review` 的平台管理人员审批；拥有 `PERMISSION_MANAGE` / `system.project.manage` 的项目管理员只能管理授权项目的已有用户访问申请、职责、模板和项目访问状态。
- OpenID、UnionID 不进入 Web DTO；手机号按现有后台管理权限展示。
- 项目暂停、恢复、微信停用、恢复、解绑、审批和拒绝均写 `sys_operation_log`，并清理权限缓存或使相关 token 失效。
- 鉴权除校验 JWT 签名外，还会校验 Redis 中 `auth:session:{tokenFingerprint}`；同一账号可同时保留 Web 与小程序等多个会话。普通登出只删除当前会话，账号/微信停用或解绑会通过 `auth:user-sessions:{userId}` 清理全部会话，旧 token 随即返回 `401`。

> **以下编号清单是旧完整巡检闭环的兼容记录，不得覆盖顶部通用 RBAC、现行极简巡检权限目录和精确项目隔离规则。**

小程序电箱台账、内部二维码解析、现场检查、整改闭环和公开扫码兼容接口遵守：

```text
1. 所有接口从 token 获取 currentUser
2. 电箱列表、模板、记录、导出接口必须按 projectId 校验项目权限
3. 带 electricBoxId 或电箱 id 的接口，必须先查询 electric_box，再按 electric_box.project_id 校验权限
4. 创建检查记录时，projectId 和 electricBoxId 必须一致，不能信任前端传入的项目归属
5. inspectorId、inspectorName、reviewerId、reviewerName 必须以后端 currentUser 为准
6. 更新、提交、复核、删除或作废检查记录时，必须先按 id 查询原记录，再按原记录 projectId 校验权限
7. 电工日检按目标项目 `INSPECTION_DAILY_SUBMIT` 权限判断，不再以电箱负责人关系作为额外限制
8. 安全员复核仅允许平台管理员、项目管理员、安全管理员
9. 整改反馈时，允许整改负责人处理自己的任务，也允许项目管理员、安全管理员、平台管理员处理授权项目内任务
10. 复查关闭或退回整改时，允许平台管理员、授权项目管理员、授权安全管理员操作
11. 单箱月表或日期范围报表允许目标项目拥有 `INSPECTION_DAILY_SUBMIT` 或 `SUMMARY_EXPORT` 的成员导出；多个电箱、全部电箱和项目级导出要求 `SUMMARY_EXPORT`
```
