# 接口规则

## 2026-07-28 统一注册、微信快捷登录与系统管理接口

本节为当前认证和权限接口的最新口径。所有路径均以 `/api/v1` 为后端前缀；Web 经 Vite `/api` 代理调用。

### 公共注册与认证

| 方法与路径 | 用途 | 关键规则 |
| --- | --- | --- |
| `GET /auth/captcha` | 获取 Web 注册图形验证码 | 验证码一次性消费；注册、登录和扫码相关接口有 Redis 限流 |
| `POST /auth/login` | 账号密码登录 | 只接受有效 BCrypt；待重置、停用或仅微信登录账号拒绝登录 |
| `POST /registration-applications` | Web/小程序提交注册申请 | 不创建用户；Web 必须带图形验证码，小程序带微信 code/会话并可使用微信手机号 |
| `POST /registration-applications/status` | 查询本人申请状态 | 只接受提交时返回的随机 `statusToken`/兼容别名，不支持按手机号、账号或申请 ID 枚举 |
| `POST /registration-applications/cancel` | 申请人取消待审批申请 | 使用同一随机状态令牌；只允许取消 `PENDING`，并立即清除密码摘要、释放账号/手机号/微信占用 |
| `GET /auth/user-info` | 获取当前完整登录上下文 | 返回菜单树、平台权限码、项目角色/权限、可访问项目和微信绑定状态 |
| `POST /auth/logout` | 注销当前会话 | 普通退出只注销当前 token；停用、改密、解绑和关键授权变化由服务端注销全部会话 |

注册申请状态固定为 `PENDING / APPROVED / REJECTED / CANCELLED`。审批通过必须在同一事务内创建 `sys_user`、写入平台角色与项目角色/范围、建立申请中的微信绑定并写审计日志；批准、驳回和申请人取消后都会清除申请表密码摘要。

### 小程序微信登录和绑定

| 方法与路径 | 用途 | 关键规则 |
| --- | --- | --- |
| `POST /auth/wechat/mini/login` | 微信快捷登录 | 只允许已绑定、账号启用且绑定有效的微信身份 |
| `POST /auth/wechat/mini/bind-login` | 绑定已有账号并完成登录 | 必须同时验证账号密码和新的 `uni.login` code，不按同手机号自动绑定 |
| `POST /auth/wechat/bind` | 当前用户绑定微信 | 同时校验系统用户、OpenID、UnionID 冲突 |
| `POST /auth/wechat/unbind` | 当前用户解绑 | 只允许已启用密码登录的账号重新验证密码后自助解绑；解绑后全会话失效 |
| `POST /users/me/wechat-bindings` | 当前用户绑定兼容入口 | 兼容旧客户端，规则与 `/auth/wechat/bind` 一致 |
| `DELETE /users/me/wechat-bindings` | 当前用户解绑兼容入口 | 兼容旧客户端，规则与 `/auth/wechat/unbind` 一致 |

同一 AppID 下，一个系统用户只能对应一个有效微信身份；有效 OpenID 和 UnionID 也不能绑定多个用户。手机号相同不构成自动绑定依据。仅微信登录账号不能自行解绑，由平台管理员在系统管理中处理。

### Web 微信扫码登录

| 方法与路径 | 调用方 | 用途 |
| --- | --- | --- |
| `POST /auth/web-qr/challenges` | Web 浏览器 | 创建 2 分钟 challenge，返回二维码、challenge ID 和仅浏览器持有的校验密钥 |
| `POST /auth/web-qr/challenges/{challengeId}/status` | 创建二维码的浏览器 | 每 2 秒查询状态；必须提交浏览器校验密钥 |
| `POST /auth/web-qr/challenges/{challengeId}/mark-scanned` | 已微信登录的小程序 | 标记已扫码并返回网站/浏览器信息 |
| `POST /auth/web-qr/challenges/{challengeId}/confirm` | 已微信登录的小程序 | 用户明确确认后生成一次性交换码 |
| `POST /auth/web-qr/challenges/{challengeId}/cancel` | 小程序或创建二维码的浏览器 | 取消本次扫码登录 |
| `POST /auth/web-qr/challenges/{challengeId}/exchange` | 创建二维码的浏览器 | 用浏览器密钥和一次性交换码兑换普通 JWT |

状态机固定为 `WAITING / SCANNED / CONFIRMED / CANCELLED / EXPIRED / CONSUMED`。二维码只包含随机 challenge 场景值，不包含 JWT 或浏览器密钥；后端必须拒绝重复确认、重复消费、过期消费、非扫码账号确认和跨浏览器兑换。扫码期间账号被停用时，最终换票同样拒绝登录。

### 系统管理

系统管理接口统一位于 `/system`：

- 注册审核：`GET /system/registration-applications`、`GET /system/registration-applications/{id}`、`POST /system/registration-applications/{id}/approve|reject`。
- 用户管理：`GET /system/users`、`GET /system/users/{userId}`、`PUT /system/users/{userId}/status|access|roles`、`POST /system/users/{userId}/reset-password`。
- 角色与权限：`GET|POST /system/roles`、`PUT /system/roles/{id}`、`PUT /system/roles/{id}/permissions`。
- 菜单与功能：`GET|POST /system/menus`、`PUT /system/menus/{id}`、`PUT /system/menus/{id}/status`、`GET|POST /system/permissions`、`PUT /system/permissions/{id}`。
- 微信绑定：`GET /system/wechat-bindings`、`PUT /system/wechat-bindings/{userId}/{bindingId}/status`、`POST /system/wechat-bindings/{userId}/{bindingId}/unbind`。
- 操作日志：`GET /system/audit-logs`。

项目成员、项目角色和原有“已有用户申请项目访问”继续复用项目成员及 `wechat-access-applications` 接口，但入口统一放在系统管理的项目授权中；该申请不能创建微信专用随机账号。同一微信在同一项目只能有一条待审批访问申请，数据库唯一键处理并发提交，批准/驳回会锁定申请行并校验更新行数。

系统管理与资料、巡检、质量接口均以后端权限码和项目范围为安全边界。`BusinessException` 现在由 `GlobalExceptionHandler` 映射为真实 HTTP `400 / 401 / 403 / 404 / 409` 等状态，同时保留统一 `Result.code`；无权限调用必须返回 HTTP `403`，前端既要处理 HTTP 状态，也要读取响应体中的业务消息。

数据库只允许执行 `backend/src/main/resources/sql/migrations/20260728_unified_registration_rbac_wechat_login.sql`，禁止执行 `init.sql`。该迁移只在副本连续演练过，且已验证重复执行不会恢复管理员主动停用的菜单或撤销的角色授权；尚未应用到正式本地库。后端微信 mock 默认关闭，只有显式 `dev/local/test` profile 才允许开启；未声明开发 profile 的启动按生产保护模式校验正式 AppID/AppSecret 和合法 HTTPS 地址。正式微信接口仍需真机验收。

## Web 与小程序三模块共用接口口径（2026-07-19）

- 资料管理统一使用 `/api/v1/document-folders` 和 `/api/v1/project-documents`；工程资料版本文件不能通过通用 `/api/v1/files` 接口查询、修改或删除，必须通过资料接口保持版本、回收站和审计关系完整。
- 巡检统一使用 `/api/v1/electric-boxes`、`/api/v1/inspection/todos` 和 `/api/v1/inspection/records`；Web 维护台账和查询汇总，小程序提交现场记录。今日已检必须存在当日有效记录，历史未闭环整改不能单独计入今日已检。
- 质量统一使用 `/api/v1/quality/issues` 和通用质量附件接口；Web 与小程序读取同一问题状态和操作日志。
- 巡检和质量照片先按约定的 `*_PENDING` 或巡检暂存类型上传，再由业务事务校验上传人、项目、暂存类型和未绑定状态后绑定业务记录。客户端业务提交失败时应删除本次尚未绑定的暂存文件。
- 已绑定到巡检记录、巡检整改或质量问题/整改/复查的附件，不能再通过通用文件更新、归档或删除接口直接修改。
- 文件预览和下载可能以 Blob 形式返回 JSON 业务错误；Web 与小程序必须先检查响应内容类型和统一 `Result.code`，不能把错误 JSON 当成文件保存或打开。

## 电箱巡检极简版接口口径（2026-07-12）

当前巡检产品保留：

- `POST /api/v1/inspection/records`：完成巡检，直接写入 `COMPLETED`，照片、备注和异常说明均可为空。
- `POST /api/v1/inspection/records/{id}/submit`：仅为旧客户端兼容，行为同样是直接完成。
- `GET /api/v1/inspection/records`、`GET /api/v1/inspection/records/{id}`：查询记录；旧 `REVIEW_* / RECTIFICATION_PENDING / CLOSED` 对外统一返回“已完成”口径，不返回复核留痕。
- `GET /api/v1/inspection/todos`：仅返回 `INSPECTION` 今日待巡检任务。
- `GET /api/v1/inspection/records/summary`：供 Web 计算月度应检、已检、漏检和异常统计，小程序不再调用。
- `GET /api/v1/inspection/records/export`：Web 与小程序共用的月表导出；传 `boxId` 时生成单台电箱单工作表正式月表，未传时保留项目级导出。
- `GET /api/v1/scan/electric-boxes/{sceneCode}`：一码两用分流。拥有 `INSPECTION_DAILY_SUBMIT` 的项目巡检员始终返回 `directAction=START_INSPECTION`；当天已有记录时同时返回 `todayRecordId`，巡检页据此只读回显。领导返回 `VIEW_RECORDS`，外部返回 `VIEW_PUBLIC_MONTHLY`。
- `GET /api/v1/public/electric-boxes/{publicCode}/monthly-records`：外部只读月表。

已退出 Controller 映射：巡检复核、复核人改派、复核日志、安全抽查，以及整改提交、改派、提醒、关闭、退回和复查接口。历史 Service、表和数据暂留用于兼容，不允许新前端继续调用这些旧接口。

## 接口基础规则

后端基础路径：`/api/v1`。

前端请求基础路径：`/api`。

Vite 代理规则位于 `frontend/vite.config.js`：

```js
proxy: {
  '/api': {
    target: 'http://localhost:8080',
    changeOrigin: true,
    rewrite: (path) => path.replace(/^\/api/, '/api/v1'),
  },
}
```

因此前端调用 `get('/projects')` 实际请求：

```text
前端：/api/projects
后端：/api/v1/projects
```

## 返回格式

大多数接口返回：

```json
{
  "code": 200,
  "message": "success",
  "data": {}
}
```

对应类：`backend/src/main/java/com/example/siteplatform/common/Result.java`。

异常规则：

- 业务异常使用 `BusinessException`。
- `GlobalExceptionHandler` 会将异常转成 `Result.error(code, message)`。
- HTTP 状态与业务码保持一致：参数错误、未登录、无权限、资源不存在和冲突分别使用 `400 / 401 / 403 / 404 / 409` 等实际状态；前端同时检查 HTTP 状态和 `res.code`。
- 文件下载接口是例外，返回 `ResponseEntity<Resource>`。

## 登录态和 token 处理方式

登录接口：

```text
POST /api/v1/auth/login
```

成功后返回：

```json
{
  "token": "JWT",
  "userId": 1,
  "username": "admin",
  "realName": "系统管理员"
}
```

前端保存位置：

- token：`localStorage.site_platform_token`
- 用户信息：`localStorage.site_platform_user`

axios 请求拦截器位于 `frontend/src/services/api.js`，会自动添加：

```http
Authorization: Bearer <token>
```

后端常见读取方式：

```java
@RequestHeader(value = "Authorization", required = false) String token
authService.getCurrentUser(token)
```

重要规则：

- 后端不能信任前端传入的 `userId`、`username`、`role`。
- 当前登录用户必须从 JWT 解析获得。
- 涉及当前用户、上传人、权限判断的数据，必须以后端登录态为准。
- 涉及 `projectId` 的接口必须校验当前用户是否有该项目权限。

当前规则：

- `AuthService.getCurrentUser` 同时校验 JWT 与 Redis 会话键；同一账号可保留多个独立会话。
- 当前正式资料、巡检、质量接口已增加通用操作权限守卫，并继续由业务服务校验项目范围；摄像头、设备等本期隐藏旧模块仍待单独补齐细粒度项目权限。

## 当前主要接口清单

### 认证接口

#### POST /api/v1/auth/login

前端方法：`login(username, password)`，文件 `frontend/src/services/auth.js`。

用途：用户登录并获取 token。

请求体：

```json
{
  "username": "example_user",
  "password": "用户设置的密码"
}
```

返回：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "token": "JWT",
    "userId": 1,
    "username": "admin",
    "realName": "系统管理员"
  }
}
```

权限：无需 token。

注意：

- 不提供默认测试账号或明文密码提示。
- 数据库存储 BCrypt 摘要，密码必须为 8–72 位并同时包含字母和数字；非 BCrypt 历史密码和待重置账号拒绝登录。
- 管理员密码只能通过系统管理重置，或在启动时同时提供一次性的 `ADMIN_RESET_USERNAME`、`ADMIN_RESET_PASSWORD` 环境变量显式重置。
- 每次登录签发带唯一 `jti` 的 JWT，并写入独立 Redis 会话，不会覆盖同一账号在其他端的 Token。

#### GET /api/v1/auth/user-info

用途：获取当前登录用户信息。

请求头：

```http
Authorization: Bearer <token>
```

返回：`CurrentUserVO`，不包含密码。

核心字段：

- `id`, `username`, `realName`, `phone`, `email`, `status`, `passwordLoginEnabled`
- `wechatBound`, `wechatBindingStatus`
- `roles`: 当前用户全局角色编码列表，例如 `PLATFORM_ADMIN`
- `menus`: 按角色聚合的菜单树
- `permissionCodes`: 平台角色聚合的通用操作权限码
- `projectRoles` / `projectContexts`: 当前用户项目级授权列表，字段包括 `projectId`、`projectName`、`shortName`、`projectRoleCode`、`permissionTemplateId`、`permissionTemplateName`、`permissionTemplateCode`、`permissionCodes`
- `accessibleProjectIds`: 当前用户可访问项目 ID 列表

说明：

- 平台管理员返回全部项目，项目职责和权限模板按 `PLATFORM_ADMIN` 表示，并拥有全部电箱巡检权限码。
- 非平台管理员按 `sys_user_project` 返回授权项目、兼容项目职责和电箱巡检权限模板。
- PC 和小程序只用该接口做按钮显隐，后端接口仍必须独立校验权限。

权限：登录用户。

#### POST /api/v1/auth/logout

用途：登出并仅删除当前 Token 对应的 Redis 会话。账号停用、微信停用或解绑时，后台仍会清理该用户全部会话。

权限：登录用户。

#### PUT /api/v1/projects/{projectId}/location

用途：更新项目定位信息。

请求体：

```json
{
  "longitude": 121.543743,
  "latitude": 31.233568,
  "province": "上海市",
  "city": "上海市",
  "district": "浦东新区",
  "address": "上海市浦东新区陆家嘴环路1000号",
  "coordinateType": "BD09"
}
```

返回：`ProjectMapPointVO`。

校验：

- `longitude`: 必填，范围 -180 到 180。
- `latitude`: 必填，范围 -90 到 90。
- `coordinateType`: 只允许 `BD09`、`GCJ02`、`WGS84`，为空默认 `BD09`。

权限：

- 平台管理员可更新。
- 对该项目有权限的项目管理员可更新。

副作用：

- 写入 `sys_operation_log`，`operationType = UPDATE_PROJECT_LOCATION`。

#### POST /api/v1/projects

用途：新增项目。

字段口径：正式业务只使用 `folderId` 和 `status`。`folderId` 是当前项目内的一级资料目录，`status` 是归档状态，仅使用 `ACTIVE`（使用中）和 `ARCHIVED`（已归档）。历史 `category` 参数和字段只为旧数据/旧客户端兼容，正式 Web 与小程序不再展示、筛选或编辑资料类型。

- `PUT /api/v1/document-folders/{id}`：重命名目录，仅平台/项目管理员。
- `DELETE /api/v1/document-folders/{id}`：删除空目录，仅平台/项目管理员。

- `GET /api/v1/project-documents/summary`：返回总数、使用中、已归档、近七日更新统计和当前用户 `canManage`；历史图纸/表格字段仅兼容旧客户端。
- `GET /api/v1/project-documents/recycle-bin`：管理员分页查询回收站。
- `GET /api/v1/project-documents/{id}`：返回资料属性、全部版本和最近操作。
- `POST /api/v1/project-documents`：`multipart/form-data` 上传资料并创建 V1。
- `POST /api/v1/project-documents/{id}/versions`：上传新版本；事务内锁定资料并递增版本号。
- `PUT /api/v1/project-documents/{id}`：修改名称、编号、一级目录和备注；历史 `category` 字段继续兼容旧客户端。
- `POST /api/v1/project-documents/{id}/archive|unarchive`：归档或管理员恢复归档。
- `DELETE /api/v1/project-documents/{id}`：逻辑删除并进入回收站。
- `POST /api/v1/project-documents/{id}/restore`：管理员从回收站恢复。
- `DELETE /api/v1/project-documents/{id}/purge`：管理员永久删除全部版本和物理文件。
- `POST /api/v1/project-documents/batch`：批量 `MOVE`、`ARCHIVE`、`DELETE`。
- `GET /api/v1/project-documents/{id}/preview|download`：预览或下载当前/指定版本，使用可选 `versionId`。
- `GET /api/v1/project-documents/activities`：按项目或资料查询操作记录。

权限：授权项目成员可查询、预览、下载和上传；上传人可维护自己的使用中资料；平台管理员和授权项目 `PROJECT_ADMIN` 可管理全部资料、目录、回收站和永久删除。所有身份从 JWT 获取，所有资料和目录均按 `projectId` 校验。

上传人：创建资料和版本时，上传用户 ID 始终从当前 JWT 获取；列表与详情展示实时查询 `sys_user.real_name`，姓名为空才回退 `username`，前端不能自行提交上传人姓名。

客户端：Web 使用完整桌面管理能力；小程序 `src/api/document.ts` 使用同一组接口，提供单条资料核心闭环和管理员目录/回收站，不建立移动端专用资料接口。

存储：默认 `file.storage.type=local`，文件落在 `file.upload.path`；可通过环境变量配置 MinIO。文件写入后数据库事务失败会补偿删除新文件。

#### POST /api/v1/inspection/records/{id}/review

用途：安全员/项目管理员复核检查记录。

请求体：

```json
{
  "reviewAction": "PASS",
  "comment": "复核说明",
  "assigneeId": 2,
  "assigneeName": "项目经理",
  "requirement": "请在3天内完成整改并上传照片",
  "problemCategory": "APPEARANCE",
  "deadline": "2026-07-05"
}
```

`reviewAction` 支持：

- `PASS`: 通过归档。
- `REJECT`: 退回。
- `RECTIFY`: 转整改，自动创建 `inspection_rectification`；未传 `deadline` 时默认期限 3 天。

业务规则：

- `PASS` 可不填 `comment`。
- `REJECT` 和 `RECTIFY` 必须填写 `comment`。
- `RECTIFY` 建议传 `assigneeId` 指定整改人；后端会校验整改人必须对当前项目有权限，姓名以后端用户表为准，不信任前端传入的 `assigneeName`。
- `RECTIFY` 可传 `problemCategory` 和 `deadline`；问题分类写入整改任务，整改期限不能早于今天。
- 未传 `assigneeId` 时，后端兜底使用电箱负责电工；若电箱未配置负责人，则会生成未指定整改人的任务，后续需在后台补派。
- 复核动作会写入 `inspection_review_log`。
- 已分配给具体安全员的记录，只允许该安全员复核；项目管理员、平台管理员或拥有 `PERMISSION_MANAGE` 的用户可越权处理和改派。

权限：`PLATFORM_ADMIN`、授权项目 `PROJECT_ADMIN`、授权项目 `SAFETY_ADMIN` 或拥有 `INSPECTION_REVIEW` 权限模板的项目成员。

#### POST /api/v1/inspection/records/{id}/assign-reviewer

用途：PC 后台改派待复核记录的当前复核人，或清空复核人进入项目共享待复核池。

请求体：

```json
{
  "reviewerId": 3,
  "comment": "改派给当班安全员"
}
```

说明：

- `reviewerId` 为空时表示取消指定复核人，记录进入未分配共享池。
- 被分配人必须拥有当前项目 `INSPECTION_REVIEW` 权限。
- 仅 `REVIEW_PENDING` 记录可改派。
- 改派会写入 `inspection_review_log`。

权限：平台管理员、项目管理员或拥有 `PERMISSION_MANAGE` 权限的项目成员。

#### GET /api/v1/inspection/records/{id}/review-logs

用途：查看检查记录复核分配、改派、通过、退回、转整改和逾期留痕。

返回：`List<InspectionReviewLogVO>`。

核心字段：

- `actionType`: `ASSIGN` / `REASSIGN` / `UNASSIGN` / `PASS` / `REJECT` / `RECTIFY` / `OVERDUE`
- `fromReviewerName`, `toReviewerName`
- `operatorName`
- `comment`
- `createTime`

权限：能查看该检查记录的登录用户。

#### GET /api/v1/inspection/records/summary

用途：获取月度巡检汇总。

查询参数：

- `projectId`: 必填。
- `boxId`: 可选。
- `month`: 可选，格式 `yyyy-MM`。

返回：应检、已检、漏检、异常、未闭环整改数量和记录列表。

统计口径：

- `shouldCheck` 表示截至统计日已经到期的应检次数，不表示电箱数量。
- 历史月份统计该月完整巡检范围；当前月份只统计到服务器当天；未来月份返回 `0`。
- `checked` 只统计巡检范围内、已到期且同箱同日去重后的有效记录。
- `missed = shouldCheck - checked`，未来日期不计入漏检。
- `records` 仍返回所选月份实际存在的巡检记录，未检任务不会伪造记录行。

#### GET /api/v1/inspection/records/export

用途：导出月度巡检 Excel。

查询参数：

- `projectId`: 必填。
- `templateCode`: 可选，默认 `ELECTRIC_BOX_DAILY`。
- `month`: 可选，格式 `yyyy-MM`。
- `boxId`: 可选。

返回：`application/vnd.openxmlformats-officedocument.spreadsheetml.sheet` 文件流。

导出规则：

- 传 `boxId`：允许 `INSPECTION_DAILY_SUBMIT` 或 `SUMMARY_EXPORT`，忽略巡检员/结果筛选，生成一个 Excel、一个电箱明细 Sheet。
- 单箱文件名为 `{电箱编号}-电箱检查记录表-{yyyy-MM}.xlsx`，包含标题、工程名称、电箱信息、安装位置和检查月份。
- 单箱明细列为日期、内外观、漏电保护器、熔断、保护接零、220V 插座、380V 插座、检查人、备注；已到期未提交显示“未检”，未来日期显示“—”，非巡检范围显示“非巡检范围”。
- 不传 `boxId`：仅允许 `SUMMARY_EXPORT`，保留项目汇总和多电箱工作表。
- 后端校验 `boxId` 必须属于 `projectId`，跨项目参数返回 `403`。

#### GET /api/v1/inspection/rectifications

用途：获取整改任务列表。

查询参数：

- `projectId`: 可选。
- `status`: 可选，`PENDING` / `COMPLETED` / `CLOSED` / `REJECTED`。

权限：按项目权限过滤。

#### GET /api/v1/inspection/rectifications/{id}

用途：获取整改详情。

返回：`InspectionRectificationVO`，包含电箱位置、整改单号、问题分类 `problemCategory`、整改前照片 ID `beforePhotoFileIds`、整改照片 ID `rectificationPhotoFileIds`、`completedAt`、`reviewTime`、`reviewComment`、`rejectCount`、`recheckDeadline`、升级提醒字段 `escalationStatus/escalationTime/escalationNote` 和整改留痕 `reviewLogs` 等展示字段。

权限：先查整改，再按 `projectId` 校验；普通用户只能查看分配给自己的整改。

#### POST /api/v1/inspection/rectifications/{id}/complete

用途：整改负责人提交整改完成。

请求体：

```json
{
  "feedback": "已更换漏电保护器并复测",
  "photoFileIds": [3, 4]
}
```

权限与规则：

- 整改责任人本人，或有 `RECTIFICATION_REVIEW` 权限的管理用户。
- 仅 `PENDING` / `REJECTED` 状态可提交。
- `feedback` 必填，`photoFileIds` 至少 1 张。
- 成功后状态转为 `COMPLETED`，写入 `completedTime` 和整改留痕 `COMPLETE`。

#### POST /api/v1/inspection/rectifications/{id}/assign

用途：安全员/项目管理员改派整改人或调整整改期限。

请求体：

```json
{
  "assigneeId": 12,
  "deadline": "2024-06-17",
  "comment": "改派给当前负责电工继续处理"
}
```

权限与规则：

- 仅有 `RECTIFICATION_REVIEW` 权限的用户可改派或调整期限。
- 已关闭整改不可改派。
- `assigneeId` 和 `deadline` 至少传一项。
- 成功后写入整改留痕 `ASSIGN`。

#### POST /api/v1/inspection/rectifications/{id}/escalate

用途：整改跟进提醒或逾期升级提醒。

请求体：

```json
{
  "note": "整改已逾期，请项目负责人跟进"
}
```

权限与规则：

- 仅有 `RECTIFICATION_REVIEW` 权限的用户可提醒或升级。
- 已关闭、已提交待复查的整改不可升级提醒。
- 未逾期写入 `REMIND` 留痕，已逾期写入 `ESCALATE` 留痕。

#### POST /api/v1/inspection/rectifications/{id}/close

用途：安全员/项目管理员复查关闭整改。

请求体：

```json
{
  "comment": "复查通过"
}
```

权限与规则：

- 仅有 `RECTIFICATION_REVIEW` 权限的用户可关闭。
- 仅 `COMPLETED` 状态可关闭。
- `comment` 可选。
- 成功后状态转为 `CLOSED`，写入 `reviewTime`、`reviewComment`、`closeTime` 和整改留痕 `CLOSE`。
- 如果同一检查记录下无未关闭整改，检查记录状态同步置为 `CLOSED`。

#### POST /api/v1/inspection/rectifications/{id}/reject

用途：安全员/项目管理员退回整改。

请求体：

```json
{
  "comment": "整改照片不清晰，现场仍有线缆裸露"
}
```

权限与规则：

- 仅有 `RECTIFICATION_REVIEW` 权限的用户可退回。
- 仅 `COMPLETED` 状态可退回。
- `comment` 必填。
- 成功后状态转为 `REJECTED`，写入 `reviewTime`、`reviewComment`，`rejectCount` 累加，`recheckDeadline` 顺延 3 天，并写入整改留痕 `REJECT`。

### 小程序照片上传与回显规则

小程序真实模式 `VITE_USE_MOCK=false` 时：

- 照片先调用 `POST /api/v1/files` 上传，必须携带 `Authorization: Bearer <token>`。
- 日检照片建议参数：`projectId`、`businessType=inspection_record`、`fileType=INSPECTION_OUTER_PHOTO|INSPECTION_INNER_PHOTO`。
- 安全抽查问题照片建议参数：`businessType=inspection_record`、`fileType=INSPECTION_PROBLEM_PHOTO`。
- 整改照片建议参数：`businessType=inspection_rectification`、`businessId=<rectificationId>`、`fileType=RECTIFICATION_PHOTO`。
- 业务接口只保存文件 ID，不直接保存匿名图片 URL。
- 图片回显通过 `GET /api/v1/files/{id}/download` 下载，仍需携带 token；小程序端用 `uni.downloadFile` 获取临时路径后展示。

#### GET /api/v1/public/electric-boxes/{publicCode}/summary

用途：外部人员扫码查看电箱近 30 天只读巡检汇总。

权限：无需登录。

访问控制：

- 仅按 `publicCode` 查询，不接受内部 `qrCode`。
- 对应电箱 `public_access_enabled = 1` 时才允许查看。
- 电箱公开访问被后台停用后，该接口返回业务错误，不继续展示历史汇总。

脱敏规则：

- 只展示项目简称、电箱编号/名称/位置、状态、近 30 天起止日期、应检/已检/漏检/异常/未闭环数量和最近记录摘要。
- `recentRecords` 仅包含 `checkDate`、`inspectedAt`、`source`、`status`、`abnormalCount`。
- 不展示手机号、账号、内部用户 ID、检查人姓名、照片文件 ID、检查项明细、备注、复核人、复核意见或复核日志。
- 不提供任何写操作。

## 新增接口要求

### 2026-07-11 电箱统一巡检码接口

- `GET/PUT /api/v1/electric-boxes/{id}/inspection-scope`：查询或变更日检范围历史区间。
- `GET/PUT /api/v1/inspection/settings/{projectId}`：查询或保存项目截止时间和提醒设置。
- `GET /api/v1/scan/electric-boxes/{sceneCode}`：可选登录态解析 `B:<publicCode>`；巡检员进入可写/只读巡检页，领导进入本箱记录，未登录或无项目权限人员进入公开月表。
- `GET /api/v1/electric-boxes/{id}/unified-code`：获取统一码预览。
- `POST /api/v1/electric-boxes/{id}/unified-code/rotate`：换码并使旧码失效。
- `GET /api/v1/public/electric-boxes/{publicCode}/monthly-records?month=yyyy-MM`：免登录公开逐日月表，限制最近 12 个月。
- `POST /api/v1/auth/wechat/session`、`POST /api/v1/auth/wechat/phone`：兼容旧扫码入口；手机号只用于判断“应绑定已有账号或应统一注册”，不能自动绑定。
- `POST /api/v1/auth/wechat/project-access`：已绑定用户扫码进入未授权项目时提交项目权限申请。
- `GET /api/v1/wechat-access-applications`：分页查询申请，支持 `projectId/status/keyword/page/size`；项目管理员只返回可管理项目。
- `POST /api/v1/wechat-access-applications/{id}/approve`：审批已有用户的项目访问。`permissionTemplateId`、项目职责、已有 `userId` 和审批意见必填；不再允许创建微信专用随机账号。
- `POST /api/v1/wechat-access-applications/{id}/reject`：拒绝申请，拒绝原因必填。

### 2026-07-12 微信绑定用户管理兼容接口

- `GET /api/v1/wechat-users`：分页查询已注册/绑定用户，支持项目、关键词、微信状态、项目状态、职责和权限模板筛选，返回 `{records,total,page,size}`。
- `GET /api/v1/wechat-users/{userId}`：平台管理员可不传 `projectId` 查看脱敏的全局管理详情；非平台管理员必须传入自己有管理权限的明确 `projectId`，且目标用户必须属于该项目。非平台管理员只返回该项目授权和该项目申请，不返回全局微信绑定历史或操作日志。所有响应均不返回 OpenID、UnionID。
- `PUT /api/v1/wechat-users/{userId}/bindings/{bindingId}/status`：平台管理员停用或恢复微信登录，原因必填；停用后当前登录令牌立即失效。
- `POST /api/v1/wechat-users/{userId}/bindings/{bindingId}/unbind`：平台管理员解绑微信，原因必填；不删除系统账号、项目授权和历史巡检记录。

权限规则：平台管理员可跨项目管理；拥有 `PERMISSION_MANAGE` 或当前项目 `system.project.manage` 的项目管理员只能在显式传入的授权项目内查询用户、申请、职责、模板和项目访问状态，不能枚举其他项目，也不能执行微信全局停用、恢复或解绑。

公开月表允许返回完整检查人姓名和业务备注，但禁止返回手机号、照片文件 ID、内部用户 ID、复核意见和操作日志。

新增接口必须：

1. 放在 `/api/v1/**` 下。
2. 使用 `Result<T>` 返回，文件流除外。
3. 明确请求参数和返回字段。
4. 需要登录的接口必须从 token 解析当前用户。
5. 涉及项目数据必须校验项目权限。
6. 不要信任前端传入的用户身份字段。
7. 写操作要考虑操作日志，至少重要业务如项目定位、删除、归档应记录。
8. 同步更新本文件和前端 `services` 封装。
