# 接口规则

## 2026-08-03 角色菜单与操作权限独立保存

| 方法与路径 | 请求 | 规则 |
| --- | --- | --- |
| `PUT /system/roles/{id}/menus` | `menuIds[]`、`businessModuleCodes[]` | 只修改菜单与三大跨端业务模块；事务内校验父子关系并清理已不属于已选菜单的操作权限。 |
| `PUT /system/roles/{id}/operation-permissions` | `permissionIds[]` | 只修改操作权限；权限必须属于已选菜单，巡检组合权限由服务端补齐技术前置项。 |
| `PUT /system/roles/{id}/permissions` | `menuIds[]`、`permissionIds[]`、可选 `businessModuleCodes[]` | 旧客户端兼容接口；新 Web 不再调用。 |
| `POST /system/roles` | 角色名称、说明、状态；`roleCode` 可选 | 未传编码时服务端生成唯一项目角色编码；旧客户端仍可提交合法编码。 |
| `PUT /system/roles/{id}` | 角色名称、说明、状态；`roleCode` 可选 | 未传编码时保留原编码；未传任何授权字段时保留现有菜单、业务模块和操作权限。 |

上述写接口只允许具有 `system.role.manage` 的平台管理员调用。项目角色不得获得
`system.*` 平台权限；`project.member.manage` 仍只允许受保护项目经理角色。
`PLATFORM_ADMIN` 的授权不可在业务界面修改。成功修改角色基本信息、菜单、操作权限或状态后，
服务端清理受影响用户的项目缓存、注销全部会话并写审计日志。

## 2026-07-31 生产配置、文档与错误响应

- 接口文档默认关闭。本地开发必须显式设置 `KNIFE4J_ENABLE=true`、
  `API_DOCS_ENABLED=true`、`SWAGGER_UI_ENABLED=true`；生产环境任一开关为真都会拒绝启动。
- 文档关闭时，`/doc.html`、`/webjars/**`、`/swagger-ui/**`、
  `/v3/api-docs/**` 由后端统一返回 HTTP `404`，不能只隐藏菜单或仅关闭 OpenAPI JSON。
- 生产数据库必须使用非 `root` 独立账号、非空密码和启用 TLS 的 `DB_URL`；Redis 必须
  提供密码。变量模板见 `backend/.env.example`，不得提交填写过真实密钥的副本。
- 参数和业务错误继续返回统一 `Result` 及对应 HTTP 状态；不存在的资源返回 HTTP
  `404`。未处理异常固定返回 HTTP/业务码 `500` 和“系统异常，请稍后重试”，文件系统、
  数据库、对象存储及第三方异常详情只写服务端日志，不得拼入客户端消息。

## 2026-07-28 统一注册、微信快捷登录与系统管理接口

本节为当前认证和权限接口的最新口径。所有路径均以 `/api/v1` 为后端前缀；Web 经 Vite `/api` 代理调用。

### 公共注册与认证

| 方法与路径 | 用途 | 关键规则 |
| --- | --- | --- |
| `GET /auth/captcha` | 获取 Web 注册图形验证码 | 验证码一次性消费；注册、登录和扫码相关接口有 Redis 限流 |
| `POST /auth/login` | 账号密码登录 | 只接受有效 BCrypt；待重置、停用或仅微信登录账号拒绝登录 |
| `POST /registration-applications` | Web/小程序提交注册申请 | 不创建用户；手机号固定为新账号登录名。`WECHAT_QUICK` 仅允许小程序提交，必须带新的微信身份 code 和手机号授权 code，仅需真实姓名；标准注册继续保存 BCrypt 密码摘要。Web 必须带图形验证码 |
| `POST /registration-applications/status` | 查询本人申请状态 | 只接受提交时返回的随机 `statusToken`/兼容别名，不支持按手机号、账号或申请 ID 枚举 |
| `POST /registration-applications/cancel` | 申请人取消待审批申请 | 使用同一随机状态令牌；只允许取消 `PENDING`，并立即清除密码摘要、释放账号/手机号/微信占用 |
| `GET /auth/user-info` | 获取当前完整登录上下文 | 返回菜单树、平台权限码，以及每个项目的 `projectRoles[]`、`menuCodes[]`、有效权限码、访问状态和微信绑定状态；Web/小程序按当前项目驱动入口。 |
| `POST /auth/initial-password` | 微信快捷注册账号设置初始密码 | 仅本人、仅 `initialPasswordSetupRequired=true` 的登录态可调用；设置 BCrypt 密码、递增凭证版本、注销旧会话并返回新 JWT |
| `POST /auth/logout` | 注销当前会话 | 普通退出只注销当前 token；停用、改密、解绑和关键授权变化由服务端注销全部会话 |

注册申请状态固定为 `PENDING / APPROVED / REJECTED / CANCELLED`。审批通过必须在同一事务内创建 `sys_user`、写入项目角色/范围、建立申请中的微信绑定并写审计日志；注册审核不得直接授予平台管理员，平台全局身份不在用户管理页分配，只能由系统初始化或受保护运维流程维护。批准、驳回和申请人取消后都会清除申请表密码摘要。

注册申请不提供自定义用户名：申请人填写或微信授权取得的 11 位手机号就是审批后系统账号的登录名。为兼容滚动升级，接口可省略 `username`；若旧客户端仍提交该字段，值必须与最终手机号完全一致，否则返回 `400`。微信快捷注册审批创建的账号写入随机 BCrypt 占位摘要、关闭密码登录并标记首次密码待设置；其首次微信登录只能获取本人状态并跳转密码设置页，业务接口、项目访问申请、微信解绑和 Web 扫码均返回 `403`，直到初始密码设置完成。

标准微信注册提交时，Redis 微信临时身份使用一次性占用标记防止并发重复消费。申请事务
提交成功后清理占用标记；字段校验、重复申请或数据库写入导致事务回滚时，恢复原临时身份
会话及 10 分钟有效期并释放占用，允许用户修正表单后重试，无需重新微信授权。

### 小程序微信登录和绑定

| 方法与路径 | 用途 | 关键规则 |
| --- | --- | --- |
| `POST /auth/wechat/mini/login` | 微信快捷登录 | 只允许已绑定、账号启用且绑定有效的微信身份 |
| `POST /auth/wechat/mini/bind-login` | 绑定已有账号并完成登录 | 必须同时验证账号密码和新的 `uni.login` code，不按同手机号自动绑定 |
| `POST /auth/wechat/bind` | 当前用户绑定微信 | 同时校验系统用户、OpenID、UnionID 冲突 |
| `POST /auth/wechat/unbind` | 当前用户解绑 | 只允许已启用密码登录的账号重新验证密码后自助解绑；解绑后全会话失效 |
| `POST /users/me/wechat-bindings` | 当前用户绑定兼容入口 | 兼容旧客户端，规则与 `/auth/wechat/bind` 一致 |
| `DELETE /users/me/wechat-bindings` | 当前用户解绑兼容入口 | 兼容旧客户端，规则与 `/auth/wechat/unbind` 一致 |

同一 AppID 下，一个系统用户只能对应一个有效微信身份；有效 OpenID 和 UnionID 也不能绑定多个用户。手机号相同不构成自动绑定依据。仅微信登录账号不能自行解绑，由平台管理员在系统管理中处理。

### Web 微信扫码登录

| 方法与路径 | 调用方 | 用途 |
| --- | --- | --- |
| `POST /auth/web-qr/challenges` | Web 浏览器 | 创建 2 分钟 challenge，返回二维码、challenge ID 和仅浏览器持有的校验密钥 |
| `POST /auth/web-qr/challenges/{challengeId}/status` | 创建二维码的浏览器 | 每 2 秒查询状态；必须提交浏览器校验密钥 |
| `POST /auth/web-qr/challenges/{challengeId}/mark-scanned` | 已微信登录的小程序 | 标记已扫码并返回网站/浏览器信息 |
| `POST /auth/web-qr/challenges/{challengeId}/confirm` | 已微信登录的小程序 | 用户明确确认后生成一次性交换码 |
| `POST /auth/web-qr/challenges/{challengeId}/cancel` | 小程序或创建二维码的浏览器 | 取消本次扫码登录 |
| `POST /auth/web-qr/challenges/{challengeId}/exchange` | 创建二维码的浏览器 | 用浏览器密钥和一次性交换码兑换普通 JWT |

状态机固定为 `WAITING / SCANNED / CONFIRMED / CANCELLED / EXPIRED / CONSUMED`。二维码只包含随机 challenge 场景值，不包含 JWT 或浏览器密钥；后端必须拒绝重复确认、重复消费、过期消费、非扫码账号确认和跨浏览器兑换。扫码期间账号被停用，或微信快捷注册账号尚未完成首次密码设置时，最终换票同样拒绝登录。

### 系统管理

系统管理接口统一位于 `/system`：

- 注册审核：`GET /system/registration-applications`、`GET /system/registration-applications/{id}`、`POST /system/registration-applications/{id}/approve|reject`。
- 用户管理：`GET /system/users`、`GET /system/users/{userId}`、`PUT /system/users/{userId}/status|access|roles`、`PUT /system/users/{userId}/project-role-assignments`、`POST /system/users/{userId}/reset-password`。用户列表额外返回完整 `projectRoles[]`；表格直接展示最多两个“项目 + 角色”摘要和超出数量。平台管理员在“项目 → 角色”树中形成待保存变更，使用批量接口一次提交，暂停/恢复仍调用单独的项目成员状态接口。
- 角色与权限：`GET|POST /system/roles`、`PUT /system/roles/{id}`、`PUT /system/roles/{id}/permissions`。
- 菜单与功能：`GET|POST /system/menus`、`PUT /system/menus/{id}`、`PUT /system/menus/{id}/status`、`GET|POST /system/permissions`、`PUT /system/permissions/{id}`。
- 微信绑定：`GET /system/wechat-bindings`、`PUT /system/wechat-bindings/{userId}/{bindingId}/status`、`POST /system/wechat-bindings/{userId}/{bindingId}/unbind`。
- 操作日志：`GET /system/audit-logs`。

角色接口的 `SystemRole` 额外返回 `businessModuleCodes: ["DOCUMENT", "INSPECTION", "QUALITY"]`；`POST|PUT /system/roles` 与 `PUT /system/roles/{id}/permissions` 可提交同名数组。该数组是资料、巡检、质量的跨端统一开关：服务端会原子同步该模块的 Web 与小程序菜单关联，同时保留 `permissionIds` 中已配置的细分操作权限。未传该字段的旧调用保持角色现有模块选择，避免兼容调用意外撤销业务模块。

Web 角色分配界面不要求录入数值角色 ID：注册审核、用户管理和项目成员管理都从现有启用项目角色中选择。用户管理使用“项目 → 角色”树，项目成员管理使用“用户 → 角色”树；父节点表示成员关系，首次勾选自动附加启用中的内置 `USER` 角色，取消最后一个角色等同待移出。`roleIds[]` 仅为接口字段，页面不展示数值 ID，也不提供用户级直接权限。`GET /project-members/roles` 返回可分配角色摘要，项目经理不会收到可授予的项目经理角色。

### 项目成员与权限

| 方法与路径 | 用途 | 关键规则 |
| --- | --- | --- |
| `GET /project-members?projectId` | 查询当前项目成员 | 返回 `projectRoles[]`、有效权限、访问状态和变更记录；项目经理仅能查询自己的项目。 |
| `GET /project-members/assignment-options?projectId&keyword&membership&pageNo&pageSize` | 分页查询“用户 → 角色”树 | `membership` 为 `ALL / ASSIGNED / UNASSIGNED`；默认每页 100、最大 100。已有成员即使账号停用仍展示，未加入候选仅含启用账号；支持姓名、账号、已分配角色搜索，不返回手机号、邮箱或其他项目关系。 |
| `GET /project-members/users?projectId&keyword` | 搜索可加入账号 | 仅项目经理或系统管理员；只返回已启用系统账号的姓名、账号和 ID，不返回手机号、邮箱或其他项目关系。 |
| `GET /project-members/roles?projectId` | 查询当前操作者可分配角色 | 项目经理不返回项目经理角色；系统管理员返回全部启用项目角色。 |
| `POST /project-members` | 加入成员/设置角色 | 请求体为 `projectId`、`userId`、`roleIds[]`；至少一个启用项目角色。 |
| `PUT /project-members/{projectId}/{userId}` | 更新成员角色 | 请求体为 `roleIds[]`，完全替换该项目内角色集合。 |
| `PUT /project-members/{projectId}/{userId}/status` | 暂停或恢复访问 | 状态仅 `ACTIVE / DISABLED`；恢复必须仍有至少一个启用角色。 |
| `PUT /project-members/{projectId}/role-assignments` | 当前项目批量新增、调整或移出成员 | `changes[{userId,operation,roleIds[]}]`；`UPSERT / REMOVE`，最多 200 项。同一事务预检全部成员、角色、项目经理保护和业务占用，任一失败整批回滚。 |
| `DELETE /project-members/{projectId}/{userId}` | 移出项目 | 同时删除成员关系和项目角色关系。 |

`PUT /system/users/{userId}/project-role-assignments` 仅平台管理员使用，请求为
`changes[{projectId,operation,roleIds[]}]`，用于“项目 → 角色”树跨项目一次保存；成功返回该用户完整项目角色列表。
两个批量接口均拒绝重复节点、未知操作、空 `UPSERT` 角色、非项目角色和超过 200 项的请求，
按项目和用户固定顺序锁定后再写入。新增成员固定 `ACTIVE`，调整暂停成员角色时保留原访问状态；
每批只执行一次批量审计并按受影响用户清理缓存和会话。原单节点接口继续兼容。

同一用户同一项目可拥有多个角色，权限并集合并。项目经理仅能在自己的项目操作普通成员，不能授予、撤销、暂停、移出或调整任何项目经理角色（也不能调整自己）；系统管理员不受这一项目内限制。角色/成员/状态变更均会记录审计日志、清理权限缓存并注销受影响用户会话。

密码、账号状态、微信绑定、项目成员授权、角色、菜单、操作权限及巡检权限模板的单记录
新增、更新或删除必须校验数据库影响行数为 1。写入未生效时返回真实 HTTP `409` 并
回滚，不得继续注销会话、替换权限或记录成功结果。

原有“已有用户申请项目访问”继续使用 `wechat-access-applications`，但入口统一放在系统管理的“项目成员与权限”；该申请不能创建微信专用随机账号。项目经理只能审批申请已匹配的账号，且列表不返回申请手机号；平台管理员可处理全部项目。同一微信在同一项目只能有一条待审批访问申请，数据库唯一键处理并发提交，批准/驳回会锁定申请行并校验更新行数。

`/inspection-permission-templates` 为历史兼容路径，全部返回 `410`；权限配置统一通过 `/system/roles`、`/system/permissions` 和 `/system/menus` 完成。

系统管理与资料、巡检、质量接口均以后端权限码和项目范围为安全边界。`BusinessException` 现在由 `GlobalExceptionHandler` 映射为真实 HTTP `400 / 401 / 403 / 404 / 409` 等状态，同时保留统一 `Result.code`；无权限调用必须返回 HTTP `403`，前端既要处理 HTTP 状态，也要读取响应体中的业务消息。

数据库只允许按顺序执行 `20260728_unified_registration_rbac_wechat_login.sql`、`20260729_project_multi_role_member_management.sql`、`20260729_project_multi_role_permission_cleanup.sql`、`20260729_shared_business_module_access.sql`、`20260729_wechat_quick_registration_initial_password.sql`、`20260730_quality_issue_resilience.sql`、`20260801_inspection_template_item_code_alignment.sql` 和 `20260803_role_menu_permission_hierarchy.sql`，禁止执行 `init.sql`。增量脚本均须在备份和目标库预检后按需执行；角色映射缺失或巡检模板新旧编码同时有效时会在写入前中止。后端微信 mock 默认关闭，只有显式 `dev/local/test` profile 才允许开启；未声明开发 profile 的启动按生产保护模式校验正式 AppID/AppSecret 和合法 HTTPS 地址。正式微信接口仍需真机验收。

## Web 与小程序三模块共用接口口径（2026-07-19）

- 资料管理统一使用 `/api/v1/document-folders` 和 `/api/v1/project-documents`；工程资料版本文件不能通过通用 `/api/v1/files` 接口查询、修改或删除，必须通过资料接口保持版本、回收站和审计关系完整。
- 巡检统一使用 `/api/v1/electric-boxes`、`/api/v1/inspection/todos` 和 `/api/v1/inspection/records`；Web 维护台账和查询汇总，小程序提交现场记录。今日已检必须存在当日有效记录，历史未闭环整改不能单独计入今日已检。
- 质量统一使用 `/api/v1/quality/issues` 和通用质量附件接口；Web 与小程序读取同一问题状态和操作日志。
- 巡检和质量照片先按约定的 `*_PENDING` 或巡检暂存类型上传，再由业务事务校验上传人、项目、暂存类型和未绑定状态后绑定业务记录。客户端业务提交失败时应删除本次尚未绑定的暂存文件。
- 已绑定到巡检记录、巡检整改或质量问题/整改/复查的附件，不能再通过通用文件更新、归档或删除接口直接修改。
- 文件预览和下载可能以 Blob 形式返回 JSON 业务错误；Web 与小程序必须先检查响应内容类型和统一 `Result.code`，不能把错误 JSON 当成文件保存或打开。

## 电箱巡检极简版接口口径（2026-07-12）

当前巡检产品保留：

- `POST /api/v1/inspection/records`：完成巡检，直接写入 `COMPLETED`，照片、备注和异常说明均可为空。
- `POST /api/v1/inspection/records/{id}/submit`：仅为旧客户端兼容，行为同样是直接完成。
- `GET /api/v1/inspection/records`、`GET /api/v1/inspection/records/{id}`：查询记录；旧 `REVIEW_* / RECTIFICATION_PENDING / CLOSED` 对外统一返回“已完成”口径，不返回复核留痕。
- `GET /api/v1/inspection/todos`：仅返回 `INSPECTION` 今日待巡检任务。
- `GET /api/v1/inspection/records/summary`：供 Web 与小程序计算月度或单日应检、已检、漏检和异常统计。
- `GET /api/v1/inspection/records/export`：继续兼容 Web 与小程序月表；Web 还可通过 `startDate/endDate/boxIds` 导出日期范围内的单箱、部分电箱或全部电箱正式报表。
- `GET /api/v1/scan/electric-boxes/{sceneCode}`：一码两用分流。拥有 `INSPECTION_DAILY_SUBMIT` 的项目巡检员始终返回 `directAction=START_INSPECTION`；当天已有记录时同时返回 `todayRecordId`，巡检页据此只读回显。领导返回 `VIEW_RECORDS`，外部返回 `VIEW_PUBLIC_MONTHLY`。
  调用者没有目标项目巡检权限且该电箱已关闭公开访问时，接口在巡检范围和当天记录查询
  前返回 HTTP `403`，不得返回电箱编号、名称、位置等元数据；匿名公开扫码不查询当天
  内部巡检记录。
- `GET /api/v1/public/electric-boxes/{publicCode}/monthly-records`：外部只读月表。

已退出 Controller 映射：巡检复核、复核人改派、复核日志、安全抽查，以及整改提交、改派、提醒、关闭、退回和复查接口。历史 Service、表和数据暂留用于兼容，不允许新前端继续调用这些旧接口。

## 接口基础规则

后端基础路径：`/api/v1`。

前端请求基础路径：`/api`。

Vite 代理规则位于 `frontend/vite.config.js`：

```js
proxy: {
  '/api': {
    target: 'http://localhost:8080',
    changeOrigin: true,
    rewrite: (path) => path.replace(/^\/api/, '/api/v1'),
  },
}
```

因此前端调用 `get('/projects')` 实际请求：

```text
前端：/api/projects
后端：/api/v1/projects
```

## 返回格式

大多数接口返回：

```json
{
  "code": 200,
  "message": "success",
  "data": {}
}
```

对应类：`backend/src/main/java/com/example/siteplatform/common/Result.java`。

异常规则：

- 业务异常使用 `BusinessException`。
- `GlobalExceptionHandler` 会将异常转成 `Result.error(code, message)`。
- HTTP 状态与业务码保持一致：参数错误、未登录、无权限、资源不存在和冲突分别使用 `400 / 401 / 403 / 404 / 409` 等实际状态；前端同时检查 HTTP 状态和 `res.code`。
- 文件下载接口是例外，返回 `ResponseEntity<Resource>`。

## 登录态和 token 处理方式

登录接口：

```text
POST /api/v1/auth/login
```

成功后返回：

```json
{
  "token": "JWT",
  "userId": 1,
  "username": "admin",
  "realName": "系统管理员"
}
```

前端保存位置：

- token：`localStorage.site_platform_token`
- 用户信息：`localStorage.site_platform_user`

axios 请求拦截器位于 `frontend/src/services/api.js`，会自动添加：

```http
Authorization: Bearer <token>
```

后端常见读取方式：

```java
@RequestHeader(value = "Authorization", required = false) String token
authService.getCurrentUser(token)
```

重要规则：

- 后端不能信任前端传入的 `userId`、`username`、`role`。
- 当前登录用户必须从 JWT 解析获得。
- 涉及当前用户、上传人、权限判断的数据，必须以后端登录态为准。
- 涉及 `projectId` 的接口必须校验当前用户是否有该项目权限。

当前规则：

- `AuthService.getCurrentUser` 同时校验 JWT 与 Redis 会话键；同一账号可保留多个独立会话。
- 当前正式资料、巡检、质量接口已增加通用操作权限守卫，并继续由业务服务校验项目范围；摄像头、设备等本期隐藏旧模块仍待单独补齐细粒度项目权限。

## 当前主要接口清单

### 认证接口

#### POST /api/v1/auth/login

前端方法：`login(username, password)`，文件 `frontend/src/services/auth.js`。

用途：用户登录并获取 token。

请求体：

```json
{
  "username": "example_user",
  "password": "用户设置的密码"
}
```

返回：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "token": "JWT",
    "userId": 1,
    "username": "admin",
    "realName": "系统管理员"
  }
}
```

权限：无需 token。

注意：

- 不提供默认测试账号或明文密码提示。
- 数据库存储 BCrypt 摘要，密码必须为 8–72 位并同时包含字母和数字；非 BCrypt 历史密码和待重置账号拒绝登录。
- 管理员密码只能通过系统管理重置，或在启动时同时提供一次性的 `ADMIN_RESET_USERNAME`、`ADMIN_RESET_PASSWORD` 环境变量显式重置。
- 每次登录签发带唯一 `jti` 的 JWT，并写入独立 Redis 会话，不会覆盖同一账号在其他端的 Token。
- 密码登录和微信绑定登录同时按真实客户端 IP、规范化账号执行两组独立限流；账号限流不随
  IP 改变而重置。Redis 键只保存使用当前环境 JWT 密钥生成的 HMAC-SHA256 摘要，不保存
  明文用户名、手机号、IP 或扫码 challenge。

#### GET /api/v1/auth/user-info

用途：获取当前登录用户信息。

请求头：

```http
Authorization: Bearer <token>
```

返回：`CurrentUserVO`，不包含密码。

核心字段：

- `id`, `username`, `realName`, `phone`, `email`, `status`, `passwordLoginEnabled`
- `wechatBound`, `wechatBindingStatus`
- `roles`: 当前用户全局角色编码列表，例如 `PLATFORM_ADMIN`
- `menus`: 按角色聚合的菜单树
- `permissionCodes`: 平台角色聚合的通用操作权限码
- `projectRoles` / `projectContexts`: 当前用户项目级授权列表，字段包括 `projectId`、`projectName`、`shortName`、`projectRoleCode`、`permissionTemplateId`、`permissionTemplateName`、`permissionTemplateCode`、`permissionCodes`
- `accessibleProjectIds`: 当前用户可访问项目 ID 列表

说明：

- 平台管理员返回全部项目，项目职责和权限模板按 `PLATFORM_ADMIN` 表示，并拥有全部电箱巡检权限码。
- 非平台管理员按 `sys_user_project` 返回授权项目、兼容项目职责和电箱巡检权限模板。
- PC 和小程序只用该接口做按钮显隐，后端接口仍必须独立校验权限。

权限：登录用户。

#### POST /api/v1/auth/logout

用途：登出并仅删除当前 Token 对应的 Redis 会话。账号停用、微信停用或解绑时，后台仍会清理该用户全部会话。

权限：登录用户。

### 质量闭环接口

后端代码：`backend/src/main/java/com/example/siteplatform/quality/`。

小程序方法：`wechat-miniprogram/site-platform-miniprogram/src/api/quality.ts`。

统一鉴权前提：质量接口必须先校验目标项目 `ACTIVE` 访问、`QUALITY` 模块和
`quality.view`；写动作再按 `quality.manage`、`quality.rectify`、`quality.review`
细分。普通项目角色与受保护项目角色使用同一权限码规则，不再额外要求
`PROJECT_ADMIN` / `SAFETY_ADMIN` 固定角色编码。

#### GET /api/v1/quality/issues

用途：按施工区域查询质量问题。参数为 `projectId`、可选 `status`、可选 `keyword`。

`status=OVERDUE` 同时包含超过整体闭环期限的 `PENDING` 与 `RECHECK`。列表统一按
“未闭环、逾期、严重程度、闭环期限、创建时间”排序。普通状态筛选只接受
`PENDING / RECHECK / CLOSED / VOIDED`，其他值返回 HTTP `400`。

#### GET /api/v1/quality/issues/page

用途：质量问题兼容分页查询，筛选和排序与原列表接口完全一致。参数额外包含
`pageNo`、`pageSize`，默认 `1 / 20`，`pageSize` 最大为 `100`，返回
`PageResult<QualityIssueVO>`。原 `GET /api/v1/quality/issues` 保留，现有客户端无需迁移。

#### GET /api/v1/quality/issues/summary

用途：返回今日新增问题、待整改、已逾期、待复查、已关闭和闭环率。参数
`projectId` 必填。为兼容现有客户端，“今日新增问题”继续使用字段
`todayCheckCount`；没有任何问题时闭环率为 `0`，不显示为 `100%`。已逾期包含
`PENDING` 与 `RECHECK`，`deadline` 表示从发起到复查关闭的整体闭环期限。
`VOIDED` 不计入逾期和闭环率分母。响应中的 `canManage` 只在当前用户对目标项目
具有 `quality.manage` 时为 `true`，不再叠加项目角色白名单。

#### GET /api/v1/quality/issues/todos

用途：返回当前用户实时派生的质量待办，`projectId` 可选。返回字段为
`id/type/title/projectId/projectName/boxCode/installLocation/dueText/targetId/businessType/priority/reviewOverdue`。

- `PENDING` 只向被指派且仍具备 `quality.rectify` 的当前用户返回
  `type=RECTIFICATION`。
- `RECHECK` 只向目标项目具备 `quality.review` 的当前用户返回
  `type=RECHECK`。
- `businessType` 固定为 `QUALITY_ISSUE`，`targetId` 为质量问题 ID；质量待办使用负数
  展示 ID，客户端使用 `businessType + targetId` 作为稳定键，避免与巡检待办冲突。
- 指定项目时强制校验该目标项目的访问权与 `quality.view`；未指定时逐项目过滤，
  不会因用户在其他项目有质量权限而泄露数据。

#### GET /api/v1/quality/issues/assignees

用途：返回当前施工区域可被指派的质量整改人。参数 `projectId` 必填，响应只包含
`userId`、`username`、`realName`、`displayName`。

候选人必须是未删除且已启用账号，并具备当前项目有效访问、质量模块、
`quality.view` 和 `quality.rectify`。平台管理员也必须满足这些目标项目条件，不能
凭平台角色绕过。该接口只要求调用方具备当前项目
`quality.view`，不复用需要项目成员管理权限的 `/project-members`。

#### GET /api/v1/quality/issues/{id}

用途：返回质量问题详情及操作留痕。

#### POST /api/v1/quality/issues

用途：发起质量检查问题并指派整改人，初始状态为 `PENDING`。`photoFileIds` 至少一项，后端校验附件项目并绑定为 `QUALITY_ISSUE`。

权限：`quality.manage`。

请求可带最长 100 字符的 `requestKey`。服务端按
`projectId + 当前发起人 + requestKey` 持久化去重；重复提交返回首次创建的问题，
不重复绑定附件、写日志或发送通知。不传或传空值时继续兼容旧客户端。

字段约束：`title` 必填且最长 200 字符；`location` 最长 200 字符；
`description` 最长 1000 字符；`severity` 只接受
`NORMAL / WARNING / DANGER`；`deadline` 不能早于当天；问题照片为 1–20 个有效
正数文件 ID。`assigneeId` 如提供必须为正数，旧客户端未提供时仍按当前用户兼容，
但最终整改人必须通过正式整改资格校验。问题编号由服务端生成 32 位随机标识，
总长度不超过数据库 `issue_no VARCHAR(40)`。

#### POST /api/v1/quality/issues/{id}/rectify

用途：整改人提交整改说明和至少一张整改照片，状态转为 `RECHECK`，并向当前项目
具备复查资格的人员生成微信提醒记录；业务闭环始终以站内待办和问题状态为准。
整改说明必填且最长 1000 字符，整改照片为 1–20 个有效正数文件 ID。

权限：必须具备 `quality.rectify`，并且是当前被指派人；同时具备
`quality.manage` 时可不受当前指派限制进行管理代办。`quality.manage` 单独不能提交
整改。

#### POST /api/v1/quality/issues/{id}/review

用途：复查通过时转 `CLOSED`，退回时转回 `PENDING`；可附加复查照片。退回后提醒
当前整改负责人。`passed` 必填；复查意见最长 1000 字符，退回时仍由服务层条件
校验为必填；复查照片最多 20 个有效正数文件 ID。

权限：`quality.review`，不再额外要求 `quality.manage` 或固定管理角色。

#### POST /api/v1/quality/issues/{id}/assign

用途：Web/小程序管理端改派整改人或调整整体闭环期限，已关闭或已作废问题不允许
操作，变更写入 `ASSIGN` 留痕并提醒当前整改负责人。整改人 ID 如提供必须为正数，
期限不能早于当天，改派说明最长 1000 字符；整改人和期限至少提供一项的条件校验
继续由服务层执行。

权限：`quality.manage`。

#### POST /api/v1/quality/issues/{id}/void

用途：作废误建、重复或不属于质量问题的记录。具备 `quality.manage` 的用户可以把
`PENDING / RECHECK` 转为 `VOIDED`；作废原因必填且最长 1000 字符。操作写入
`VOID` 留痕，作废后不可整改、复查或改派，不计入逾期和闭环率分母。

整改、复查、改派和作废均以读取到的原状态和 `version` 作条件更新；并发操作只有一个
能够成功，其他请求返回 HTTP `409` 并要求刷新。微信提醒写入失败不会回滚业务状态。

统一权限：列表、统计和详情需要 `quality.view`；创建、改派、期限调整和作废需要
`quality.manage`；整改需要 `quality.rectify` 且满足“本人被指派或同时具备
`quality.manage`”；复查通过和退回只需要 `quality.review`。上述动作均继续要求目标
项目 `ACTIVE` 访问和 `QUALITY` 模块，不附加固定项目角色白名单。创建与改派使用同一
整改人资格校验，不能把问题指派给停用账号、暂停成员、质量模块不可见或缺少查看/整改
权限的人员。操作人一律从 token 解析，不接受前端伪造。所有质量写接口的 JSON 请求体
都经过 Jakarta Validation，字段缺失、超长、非法枚举、非法 ID 或过去日期统一返回
真实 HTTP `400`；退回意见、改派至少一项等条件约束继续由服务层校验。

最长 500 字符。服务端必须在存储物理文件前完成校验，超长字段返回 HTTP `400`，不得
交给数据库产生截断错误或 HTTP `500`。

写入完整性：目录、文件元数据、资料主记录、版本、当前版本指针、归档/回收站状态、
恢复、永久删除及操作日志的单记录写入都要求数据库影响行数为 1。任一步未生效返回
HTTP `409` 并回滚；上传事务回滚时清理本次新物理文件，永久删除仍只在数据库提交后
清理旧物理文件。批量操作中任一资料失败时整个事务回滚，不返回部分成功。

权限：授权项目成员可查询、预览、下载和上传；上传人可维护自己的使用中资料；平台管理员和授权项目 `PROJECT_ADMIN` 可管理全部资料、目录、回收站和永久删除。所有身份从 JWT 获取，所有资料和目录均按 `projectId` 校验。

上传人：创建资料和版本时，上传用户 ID 始终从当前 JWT 获取；列表与详情展示实时查询 `sys_user.real_name`，姓名为空才回退 `username`，前端不能自行提交上传人姓名。

客户端：Web 使用完整桌面管理能力；小程序 `src/api/document.ts` 使用同一组接口，提供单条资料核心闭环和管理员目录/回收站，不建立移动端专用资料接口。

存储：默认 `file.storage.type=local`，文件落在 `file.upload.path`；可通过环境变量配置 MinIO。文件写入后数据库事务失败会补偿删除新文件。

上传安全：单个工程资料最大 50MB；服务端同时校验扩展名和文件头，支持 PDF、栅格图片、
Office/WPS、CAD、安全文本和常见压缩包，拒绝 HTML、SVG、脚本和可执行文件。只有 PDF
与栅格图片允许 `inline`，其他格式即使调用预览接口也会强制 `attachment`；全部文件流
返回 `X-Content-Type-Options: nosniff`。

#### POST /api/v1/project-documents/{id}/client-actions

用途：在小程序完成原生客户端文件操作后，为目标资料和版本补充操作留痕。下载接口原有的“下载”记录继续保留，本接口只记录下载之后的最终客户端动作。

请求体：

```json
{
  "action": "OPEN_SAVE_MENU",
  "versionId": 123
}
```

`action` 只允许：

- `OPEN_SAVE_MENU`：PDF 或 Office 文档已由 `openDocument({ showMenu: true })` 成功打开，操作记录显示“打开保存菜单”。
- `SHARE_WECHAT_FILE`：`wx.shareFileMessage` 已成功完成文件发送，操作记录显示“发送文件”。

返回：`Result<ProjectDocumentActivityVO>`，内容为本次新增的资料操作记录。

权限与校验：

- 沿用资料查看权限；服务端先查询路径中的资料，再按资料真实 `projectId` 校验当前 JWT 用户。
- `versionId` 可省略，省略时使用资料当前版本；传入时必须属于路径中的目标资料，当前版本和历史版本执行相同校验。
- 客户端只有在微信原生 API 成功回调后才调用本接口；用户取消、格式不支持、基础库过低、下载失败或原生操作失败均不写对应的最终动作记录。
- 本接口复用现有 `sys_operation_log` 与 `PROJECT_DOCUMENT_{projectId}` 业务类型，不新增数据库表、字段或迁移。

#### POST /api/v1/files

用途：上传文件。

Content-Type：`multipart/form-data`。

表单字段：

- `file`: 必填。
- `projectId`: 必填。
- `fileName`: 可选。
- `fileType`: 默认 `其他`。
- `businessType`: 可选。
- `businessId`: 可选。
- `remark`: 可选。

返回：`FileResource`。

规则：

- 同一项目下未删除文件不允许同名。
- 文件存储目录取 `file.upload.path`，默认 `./uploads`。
- `uploaderId` 使用当前登录用户 ID。
- 新上传文件的 `status` 固定写为 `UPLOADED`。
- 人员证件附件还必须以 `PERSON_CERTIFICATE` 类型上传；未绑定附件只能由上传人本人
  绑定，已绑定附件不能被其他证件抢占。质量附件继续使用各自暂存业务类型。
- 服务端同时校验文件大小、扩展名和文件头，不信任浏览器 `accept` 或客户端 MIME。
- 巡检及质量流程照片只允许 JPG/JPEG、PNG、GIF、WebP、BMP、HEIC/HEIF，单张最大
  15MB；其他通用业务附件沿用工程资料安全白名单，最大 50MB。
- 全局 multipart 超过 50MB 返回 HTTP/业务码 `413`，不再返回笼统 `500`。

权限：上传前校验目标项目访问权。质量附件只允许以下类型：

- `QUALITY_PENDING`：需要 `quality.manage`；
- `QUALITY_RECTIFICATION_PENDING`：需要 `quality.rectify`；
- `QUALITY_REVIEW_PENDING`：需要 `quality.review`；
- `QUALITY_DOCUMENT`：需要 `quality.manage`，由 PC 端人工维护。

这些权限均在上传目标项目的 `ACTIVE` 范围和 `QUALITY` 模块内生效；普通项目角色
可以通过相应细分权限上传，不再附加 `PROJECT_ADMIN` / `SAFETY_ADMIN` 角色门槛。

上述质量类型上传时 `businessId` 必须为空。客户端不能直接上传
`QUALITY_ISSUE / QUALITY_RECTIFICATION / QUALITY_REVIEW` 最终附件；最终类型只能由
质量业务事务校验上传人、真实项目、暂存阶段及未绑定状态后转换。工程资料仍必须通过
独立资料管理接口上传。

质量暂存附件清理：

- 定时任务只处理 `QUALITY_PENDING`、`QUALITY_RECTIFICATION_PENDING`、`QUALITY_REVIEW_PENDING` 三种暂存类型，并同时要求 `business_id IS NULL` 且 `create_time` 早于 TTL 截止时间。
- 默认 TTL 为 24 小时、每小时执行一次、单批最多 200 条；可通过 `QUALITY_STAGING_CLEANUP_ENABLED`、`QUALITY_STAGING_CLEANUP_TTL_HOURS`、`QUALITY_STAGING_CLEANUP_BATCH_SIZE`、`QUALITY_STAGING_CLEANUP_INITIAL_DELAY_MS`、`QUALITY_STAGING_CLEANUP_FIXED_DELAY_MS` 配置。
- 清理前以条件更新抢占记录，业务绑定先完成时清理会跳过；清理先抢占时业务提交会失败并要求重新上传，避免已进入质量闭环的附件被误删。
- 物理文件删除成功后才永久删除元数据；单文件失败保留可重试记录、写入服务日志并继续处理后续文件。最终质量附件、`QUALITY_DOCUMENT`、工程资料和巡检附件不在该任务范围内。

#### POST /api/v1/inspection/records

用途：新增电箱日检记录。当前极简巡检模式不再通过该接口新增安全员抽查。

请求体核心字段：

```json
{
  "projectId": 1,
  "electricBoxId": 1,
  "templateCode": "ELECTRIC_BOX_DAILY",
  "source": "ELECTRICIAN_DAILY",
  "problemCategory": "APPEARANCE",
  "checkDate": "2026-06-29",
  "outerPhotoFileIds": [1],
  "innerPhotoFileIds": [2],
  "remark": "现场正常",
  "items": [
    { "itemCode": "APPEARANCE", "itemName": "内外观", "result": "NORMAL" }
  ]
}
```

业务规则：

- 服务端固定写入 `templateCode=ELECTRIC_BOX_DAILY`、`source=ELECTRICIAN_DAILY`，并忽略客户端伪造的模板、来源、问题分类和检查项名称。

- 每项结果只允许 `NORMAL`（正常）、`ABNORMAL`（异常）、`NA`（不适用）。
- 任一检查项为 `ABNORMAL` 时，`description` 必填且最长 500 字符；总备注最长 1000 字符。本轮不支持单项异常照片，只使用外观/内部照片。
- 仅允许补录今天及往前 7 天，不能填未来日期。
- 服务端先对目标电箱行加锁，再检查同一电箱同一天只能存在一条有效日检；`REVIEW_REJECTED` 退回记录不计入有效重复，并发冲突返回 HTTP `409`。
- 巡检主记录、六条检查项和巡检设置均要求数据库影响行数为 1；未生效返回 HTTP `409` 并回滚整次写入和附件绑定。
- 项目内拥有 `INSPECTION_DAILY_SUBMIT` 的用户可巡检本项目任意启用且处于巡检范围内的电箱，不再依赖电箱负责人关系。

用途：安全员/项目管理员复核检查记录。

#### GET /api/v1/inspection/records/summary

用途：获取月度或单日巡检汇总。

查询参数：

- `projectId`: 必填。
- `boxId`: 可选。
- `month`: 可选，格式 `yyyy-MM`。
- `checkDate`: 可选，格式 `yyyy-MM-dd`。

`month` 与 `checkDate` 不能同时提交；格式不合法或 `checkDate` 为未来日期时返回 HTTP `400`。返回值新增：

- `periodType`: `MONTH` / `DAY`。
- `periodValue`: 对应的 `yyyy-MM` / `yyyy-MM-dd`。
- `month`: 继续保留，兼容只识别月度字段的旧客户端；日模式取所选日期所在月份。

返回：应检、已检、漏检、异常、未闭环整改数量和记录列表。

统计口径：

- 月模式下，`shouldCheck` 表示截至统计日已经到期的应检箱次，不表示电箱数量。
- 历史月份统计该月完整巡检范围；当前月份只统计到服务器当天；未来月份返回 `0`。
- `checked` 只统计巡检范围内、已到期且同箱同日去重后的有效记录。
- `missed = shouldCheck - checked`，未来日期不计入漏检。
- `records` 仍返回所选月份实际存在的巡检记录，未检任务不会伪造记录行。
- 日模式选择全部电箱时，`shouldCheck / checked / missed / abnormal` 分别表示当日应检、已检、未检和异常电箱数；选择指定电箱时各指标为 `0` 或 `1`。统计按该日有效巡检范围计算，同箱同日多条有效记录只计一次。

#### GET /api/v1/inspection/records/export

用途：导出月度巡检 Excel，或按日选择日期范围生成正式巡检报表。

查询参数：

- `projectId`: 必填。
- `templateCode`: 可选，默认 `ELECTRIC_BOX_DAILY`。
- `month`: 旧月报参数，可选，格式 `yyyy-MM`。
- `boxId`: 旧单箱月报参数，可选。
- `startDate`: 日期范围报表开始日期，格式 `yyyy-MM-dd`，与 `endDate` 同时传入。
- `endDate`: 日期范围报表结束日期，格式 `yyyy-MM-dd`，不得晚于服务器当天。
- `boxIds`: 日期范围报表的电箱 ID，英文逗号分隔；不传表示当前项目全部电箱。

返回：`application/vnd.openxmlformats-officedocument.spreadsheetml.sheet` 文件流。

导出规则：

- 旧月报继续使用 `month/boxId`；日期范围报表使用 `startDate/endDate/boxIds`，两组参数不得混用。
- 日期范围首尾均包含，最长 366 天；开始日期晚于结束日期、结束日期晚于当天或范围超过上限均返回 HTTP `400`。
- 日期范围正式报表不接受 `inspectorId/result` 筛选；Web 页面上的巡检员和结果筛选不会影响报表。
- 传单个 `boxId` 或单个 `boxIds`：允许 `INSPECTION_DAILY_SUBMIT` 或 `SUMMARY_EXPORT`，生成一个 Excel、一个电箱正式明细 Sheet。
- 单箱文件名为 `{电箱编号}-电箱检查记录表-{yyyy-MM}.xlsx`，包含标题、工程名称、电箱信息、安装位置和检查月份。
- 日期范围单箱文件名为 `{电箱编号}-电箱检查记录表-{开始日期}至{结束日期}.xlsx`，表内标注检查区间且只生成范围内日期行。
- 单箱明细列为日期、内外观、漏电保护器、熔断、保护接零、220V 插座、380V 插座、检查人、备注；已到期未提交显示“未检”，未来日期显示“—”，非巡检范围显示“非巡检范围”。
- 传多个 `boxIds` 或不传任何电箱参数：仅允许 `SUMMARY_EXPORT`，生成巡检汇总和每个目标电箱的明细 Sheet。
- 日期范围汇总的应检、已检、漏检和异常按范围内历史巡检范围计算；检查项和范围历史批量加载，不逐日查询数据库。
- 后端校验所有电箱必须存在且属于 `projectId`，跨项目参数返回 HTTP `403`。

#### GET /api/v1/inspection/rectifications

用途：获取整改任务列表。

查询参数：

- `projectId`: 可选。
- `status`: 可选，`PENDING` / `COMPLETED` / `CLOSED` / `REJECTED`。

权限：按项目权限过滤。

#### GET /api/v1/inspection/rectifications/{id}

用途：获取整改详情。

返回：`InspectionRectificationVO`，包含电箱位置、整改单号、问题分类 `problemCategory`、整改前照片 ID `beforePhotoFileIds`、整改照片 ID `rectificationPhotoFileIds`、`completedAt`、`reviewTime`、`reviewComment`、`rejectCount`、`recheckDeadline`、升级提醒字段 `escalationStatus/escalationTime/escalationNote` 和整改留痕 `reviewLogs` 等展示字段。

权限：先查整改，再按 `projectId` 校验；普通用户只能查看分配给自己的整改。

#### POST /api/v1/inspection/rectifications/{id}/complete

用途：整改负责人提交整改完成。

请求体：

```json
{
  "feedback": "已更换漏电保护器并复测",
  "photoFileIds": [3, 4]
}
```

权限与规则：

- 整改责任人本人，或有 `RECTIFICATION_REVIEW` 权限的管理用户。
- 仅 `PENDING` / `REJECTED` 状态可提交。
- `feedback` 必填，`photoFileIds` 至少 1 张。
- 成功后状态转为 `COMPLETED`，写入 `completedTime` 和整改留痕 `COMPLETE`。

#### POST /api/v1/inspection/rectifications/{id}/assign

用途：安全员/项目管理员改派整改人或调整整改期限。

请求体：

```json
{
  "assigneeId": 12,
  "deadline": "2024-06-17",
  "comment": "改派给当前负责电工继续处理"
}
```

权限与规则：

- 仅有 `RECTIFICATION_REVIEW` 权限的用户可改派或调整期限。
- 已关闭整改不可改派。
- `assigneeId` 和 `deadline` 至少传一项。
- 成功后写入整改留痕 `ASSIGN`。

#### POST /api/v1/inspection/rectifications/{id}/escalate

用途：整改跟进提醒或逾期升级提醒。

请求体：

```json
{
  "note": "整改已逾期，请项目负责人跟进"
}
```

权限与规则：

- 仅有 `RECTIFICATION_REVIEW` 权限的用户可提醒或升级。
- 已关闭、已提交待复查的整改不可升级提醒。
- 未逾期写入 `REMIND` 留痕，已逾期写入 `ESCALATE` 留痕。

#### POST /api/v1/inspection/rectifications/{id}/close

用途：安全员/项目管理员复查关闭整改。

请求体：

```json
{
  "comment": "复查通过"
}
```

权限与规则：

- 仅有 `RECTIFICATION_REVIEW` 权限的用户可关闭。
- 仅 `COMPLETED` 状态可关闭。
- `comment` 可选。
- 成功后状态转为 `CLOSED`，写入 `reviewTime`、`reviewComment`、`closeTime` 和整改留痕 `CLOSE`。
- 如果同一检查记录下无未关闭整改，检查记录状态同步置为 `CLOSED`。

#### POST /api/v1/inspection/rectifications/{id}/reject

用途：安全员/项目管理员退回整改。

请求体：

```json
{
  "comment": "整改照片不清晰，现场仍有线缆裸露"
}
```

权限与规则：

- 仅有 `RECTIFICATION_REVIEW` 权限的用户可退回。
- 仅 `COMPLETED` 状态可退回。
- `comment` 必填。
- 成功后状态转为 `REJECTED`，写入 `reviewTime`、`reviewComment`，`rejectCount` 累加，`recheckDeadline` 顺延 3 天，并写入整改留痕 `REJECT`。

### 小程序照片上传与回显规则

小程序真实模式 `VITE_USE_MOCK=false` 时：

- 照片先调用 `POST /api/v1/files` 上传，必须携带 `Authorization: Bearer <token>`。
- 日检照片建议参数：`projectId`、`businessType=inspection_record`、`fileType=INSPECTION_OUTER_PHOTO|INSPECTION_INNER_PHOTO`。
- 首次提交日检时记录尚未生成，上传照片必须省略 `businessId`，不得传空值、`undefined` 或其他占位字符串；创建巡检记录时，服务端根据照片文件 ID 在同一事务内完成业务绑定。
- 安全抽查问题照片建议参数：`businessType=inspection_record`、`fileType=INSPECTION_PROBLEM_PHOTO`。
- 整改照片建议参数：`businessType=inspection_rectification`、`businessId=<rectificationId>`、`fileType=RECTIFICATION_PHOTO`。
- 业务接口只保存文件 ID，不直接保存匿名图片 URL。
- 图片回显通过 `GET /api/v1/files/{id}/download` 下载，仍需携带 token；小程序端用 `uni.downloadFile` 获取临时路径后展示。

### 公开扫码接口

后端代码：`backend/src/main/java/com/example/siteplatform/inspection/controller/PublicElectricBoxController.java`。

#### GET /api/v1/public/electric-boxes/{publicCode}/summary

用途：外部人员扫码查看电箱近 30 天只读巡检汇总。

权限：无需登录。

访问控制：

- 仅按 `publicCode` 查询，不接受内部 `qrCode`。
- 对应电箱 `public_access_enabled = 1` 时才允许查看。
- 电箱公开访问被后台停用后，该接口返回业务错误，不继续展示历史汇总。
- 近 30 天摘要按真实客户端 IP 每 10 分钟最多 60 次；公开逐日月表每 10 分钟最多
  30 次。限流必须在巡检范围和记录查询前执行，超限返回 HTTP `429`。

脱敏规则：

- 只展示项目简称、电箱编号/名称/位置、状态、近 30 天起止日期、应检/已检/漏检/异常/未闭环数量和最近记录摘要。
- 近 30 天应检、已检、漏检和异常按每天生效的历史巡检范围计算并按箱日去重；建箱前、
  非巡检范围和未来日期不计入，`missedDays = shouldCheckDays - checkedDays`。
- 近 30 天摘要和公开逐日月表应一次加载目标日期范围的巡检范围历史，不得按自然日逐次
  查询数据库；批量解析不能改变历史范围和建箱日期口径。
- `recentRecords` 仅包含 `checkDate`、`inspectedAt`、`source`、`status`、`abnormalCount`。
- 不展示手机号、账号、内部用户 ID、检查人姓名、照片文件 ID、检查项明细、备注、复核人、复核意见或复核日志。
- 不提供任何写操作。

## 新增接口要求

### 2026-07-11 电箱统一巡检码接口

- `GET/PUT /api/v1/electric-boxes/{id}/inspection-scope`：查询或变更日检范围历史区间。变更前
  服务端锁定目标电箱，关闭旧开放区间并新增历史区间；任一步影响行数不是 1 时返回 HTTP
  `409` 并回滚。`reason` 最长 300 字符，操作人 ID/姓名来自登录态。
- `GET/PUT /api/v1/inspection/settings/{projectId}`：查询或保存项目截止时间和提醒设置。
- `GET /api/v1/scan/electric-boxes/{sceneCode}`：可选登录态解析 `B:<publicCode>`；巡检员进入可写/只读巡检页，领导进入本箱记录，未登录或无项目权限人员进入公开月表。
  该免登录入口按真实客户端 IP 每 10 分钟最多 60 次，并在可选登录态解析和业务查询前
  限流；超限返回 HTTP `429`。
- `GET /api/v1/electric-boxes/{id}/unified-code`：获取统一码预览。
- `POST /api/v1/electric-boxes/{id}/unified-code/rotate`：换码并使旧码失效。
- `GET /api/v1/public/electric-boxes/{publicCode}/monthly-records?month=yyyy-MM`：免登录公开逐日月表，限制最近 12 个月。
- `POST /api/v1/auth/wechat/session`、`POST /api/v1/auth/wechat/phone`：兼容旧扫码入口；手机号只用于判断“应绑定已有账号或应统一注册”，不能自动绑定。
- `POST /api/v1/auth/wechat/project-access`：已绑定用户扫码进入未授权项目时提交项目权限申请。
- `GET /api/v1/wechat-access-applications`：分页查询申请，支持 `projectId/status/keyword/page/size`；项目管理员只返回可管理项目。
- `POST /api/v1/wechat-access-applications/{id}/approve`：审批已有用户的项目访问。`permissionTemplateId`、项目职责、已有 `userId` 和审批意见必填；不再允许创建微信专用随机账号。
- `POST /api/v1/wechat-access-applications/{id}/reject`：拒绝申请，拒绝原因必填。

### 2026-07-12 微信绑定用户管理兼容接口

- `GET /api/v1/wechat-users`：分页查询已注册/绑定用户，支持项目、关键词、微信状态、项目状态、职责和权限模板筛选，返回 `{records,total,page,size}`。
- `GET /api/v1/wechat-users/{userId}`：平台管理员可不传 `projectId` 查看脱敏的全局管理详情；非平台管理员必须传入自己有管理权限的明确 `projectId`，且目标用户必须属于该项目。非平台管理员只返回该项目授权和该项目申请，不返回全局微信绑定历史或操作日志。所有响应均不返回 OpenID、UnionID。
- `PUT /api/v1/wechat-users/{userId}/bindings/{bindingId}/status`：平台管理员停用或恢复微信登录，原因必填；停用后当前登录令牌立即失效。
- `POST /api/v1/wechat-users/{userId}/bindings/{bindingId}/unbind`：平台管理员解绑微信，原因必填；不删除系统账号、项目授权和历史巡检记录。

权限规则：平台管理员可跨项目管理；拥有 `PERMISSION_MANAGE` 或当前项目 `system.project.manage` 的项目管理员只能在显式传入的授权项目内查询用户、申请、职责、模板和项目访问状态，不能枚举其他项目，也不能执行微信全局停用、恢复或解绑。

公开月表允许返回完整检查人姓名和业务备注，但禁止返回手机号、照片文件 ID、内部用户 ID、复核意见和操作日志。

新增接口必须：

1. 放在 `/api/v1/**` 下。
2. 使用 `Result<T>` 返回，文件流除外。
3. 明确请求参数和返回字段。
4. 需要登录的接口必须从 token 解析当前用户。
5. 涉及项目数据必须校验项目权限。
6. 不要信任前端传入的用户身份字段。
7. 写操作要考虑操作日志，至少重要业务如项目定位、删除、归档应记录。
8. 同步更新本文件和前端 `services` 封装。

前端把接口业务字段写入打印页、下载 HTML 或其他字符串模板时必须做 HTML 文本/属性转义，
并通过 CSP 限制资源；服务端返回的 SVG 或 Data URL 不能作为任意原始标记直接拼接。

当前账号微信绑定、解绑和项目访问申请属于敏感自助操作，必须同时按受信客户端 IP 和
规范化账号限流；所有兼容入口共享同一业务额度，解绑密码校验不得在限流之前执行。
