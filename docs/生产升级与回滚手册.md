# 生产升级与回滚手册

更新时间：2026-09-02。

本文只描述当前代码从旧生产版本升级到当前增量基线的安全步骤。实际主机目录、服务名、
Nginx 配置和密钥必须以生产运维配置为准；仓库不保存这些信息。未经明确生产发布授权，
不得执行本文的写操作。

本次 2026-09-01 发布的可执行入口是 `docs/阿里云正式更新步骤.md` 和
`scripts/production-release/`。脚本内嵌的 `baseline/expected-tables.txt`、
`baseline/expected-migration-markers.txt` 和 `baseline/migration-plan.tsv` 分别固化 68 张旧表、
13 个旧标记和 11 项迁移顺序/SHA-256/逐步期望。若本文的历史背景说明与脚本门禁不一致，
必须停止发布而不是绕过脚本。

## 二、发布前硬门槛

以下任一条件不满足时停止发布：

1. 已取得明确的生产发布和服务重启授权。
2. 已确认主机、SSH Host、后端服务名、JAR 路径、运行用户、Nginx upstream 和日志路径。
3. 当前发布源码有可追溯版本。不得直接发布无法归属的脏工作树；应先确认变更范围，
   建立提交或保存不可变源码归档，并记录 SHA-256。
   若尚未形成提交，可在所有构建和测试完成后执行
   `./scripts/create-release-source-snapshot.sh /已确认的仓库外输出目录`。脚本会收集已跟踪文件和
   未忽略的未跟踪文件（明确排除本地 `backups/`），生成逐文件 SHA-256、源码状态清单及外层归档
   校验和；脚本使用私有文件权限并对打包前后的逐文件内容指纹复核。打包期间源码或工作树状态变化、
   输出目录位于项目内，或发现私密 `.env`、密钥、数据库/附件归档时会拒绝生成。该归档只建立
   可追溯源码基线，不能
   代替代码审查、正式提交、构建验证或生产发布授权。
4. 已备份生产数据库、文件存储、本地上传目录、当前 JAR、服务配置和 Nginx 配置，
   且备份能在隔离环境读取。
5. 已从生产库只读核对表数、`sys_data_migration`、重复手机号、有效微信绑定、项目角色
   映射和至少一个可恢复的平台管理员，详见 `docs/数据库结构.md`。
6. 已在生产库副本按相同顺序演练迁移和当前 JAR 启动；不使用本地开发库结果代替。
7. 已准备维护窗口、失败判定人、回滚负责人和回滚截止点。
8. 已从同一已验签生产包安装并执行 `05-self-heal-control.sh verify`；安装过程没有改变主服务
   `InvocationID` 或 `MainPID`，watchdog timer 已启用且本机验证码健康。
9. 生产环境变量满足 `backend/.env.example`，但真实值只进入部署平台密钥设置：
   - 非 `root` MySQL 账号、非空密码、TLS `DB_URL`；
   - Redis 密码；
   - 独立且至少 32 字节的 JWT 密钥；
   - 与 JWT 等密钥分离、至少 32 字节的 `VISITOR_DATA_ENCRYPTION_KEY`；
   - 分别独立、至少 32 字节的 `SEAL_SCENE_ENCRYPTION_KEY` 和
     `DOCUMENT_CIRCULATION_SCENE_ENCRYPTION_KEY`；
   - 正式微信 AppID/AppSecret、HTTPS 域名和回跳地址；
   - `FORWARD_HEADERS_STRATEGY=NATIVE`；
   - `KNIFE4J_ENABLE=false`、`API_DOCS_ENABLED=false`、
     `SWAGGER_UI_ENABLED=false`。

Nginx 必须覆盖设置并向后端传递受信代理头：

```nginx
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
```

图纸分片接口每次只接收一个 8MB 分片，不得把全站或全部 `/api` 的请求上限调到
200MB。Nginx 应只对 `/api/v1/document-uploads/{sessionId}/chunks/{index}` 的更具体
location 配置 `client_max_body_size 10m`、`proxy_request_buffering off`、
`proxy_read_timeout 300s` 和 `proxy_send_timeout 300s`，并复用站点现有 upstream 及上述受信代理头。

后端 `8080` 端口不得直接暴露公网。若实际代理不在 Tomcat 默认受信的回环/私网地址范围，
必须先明确代理地址并收窄配置，不能通过信任任意来源的转发头绕过。

## 三、备份要求

备份名必须包含 UTC/北京时间戳和源版本。至少保存：

- `mysqldump --single-transaction --routines --triggers --events` 生成的完整数据库备份；
- 当前文件存储：本地 `uploads` 或 MinIO 对应 bucket 的版本化快照；
- 当前后端 JAR 及 SHA-256；
- systemd/容器/进程管理配置和实际环境变量键清单（密钥值不得写入仓库或工单正文）；
- Nginx 站点配置；
- 当前 Web 静态目录；
- 发布前接口响应、数据库表数和关键业务数量。

数据库认证应使用服务器受控的客户端配置或密钥注入，不把密码写入命令行、shell 历史、
仓库文件或聊天记录。完成备份后必须至少执行解压、清单和校验和检查；未验证的备份不视为
可回滚备份。

### 历史访客开发密钥一次性修复

若发布前只读 `VERIFY` 发现少量历史外访密文使用早期开发默认密钥，不得把开发密钥改成生产密钥，
也不得给在线接口增加双密钥回退。当前 JAR 提供默认关闭的一次性离线工具，必须在维护窗口、旧服务
停止且数据库备份已经校验后分两阶段运行：

1. 沿用生产部署平台已注入的数据库、Redis、JWT、微信和三项业务加密密钥；不得把密钥写进命令行、
   日志或发布包。
2. 先以 `prod,visitor-legacy-reencrypt` Profile、`spring.main.web-application-type=none`、
   `app.scheduling.enabled=false` 和 `site-access.legacy-reencryption.enabled=true` 运行 `VERIFY`。
   只记录输出的总数、当前密钥数、历史密钥数、令牌摘要匹配数及候选 SHA-256 指纹。
3. 只有未知密文为 0、历史候选只落在工具核定的邀请令牌/接待人手机号/邀请审计快照三类字段，且
   同一停机窗口内数据未漂移时，才把本次 `VERIFY` 的五项结果原样传给 `APPLY`。确认短语固定为
   `APPLY_VISITOR_LEGACY_REENCRYPT_V1`；任一计数、指纹、原密文或字段白名单变化都会整笔回滚。
4. `APPLY` 完成后必须看到 `20260901_SITE_ACCESS_REENCRYPT_LEGACY_DEVELOPMENT_KEY_V1` 唯一标记，
   再运行一次 `VERIFY`，确认全部密文均由当前生产密钥解开、历史候选和未知密文均为 0。
5. 删除一次性 Profile/开关后才可按正常 `prod` Profile 启动服务。正式库实时结果必须重新获取，
   不得套用开发副本中的计数或候选指纹。

离线工具静态扫描单次预约、常用访客资料、门卫登记及会议登记的全部 22 个 AES-GCM 字段；发现
未登记字段、非核定旧密钥字段、令牌摘要不符、手机号格式异常、审计快照不是 JSON 对象或未知密文
时都会拒绝写入。修复不修改业务版本、更新时间、令牌摘要或身份 HMAC。

## 五、后端发布

正式 JAR 不允许直接从工作区运行普通 `mvn package` 后手工复制。先生成不可变源码归档，再在该归档
所在源码中执行 `scripts/build-backend-release.sh <源码归档> <仓库外输出目录>`。脚本会完整运行后端
测试，并通过 Maven `build-info` 把源码归档中 `SOURCE_MANIFEST.txt` 的 SHA-256 写入
`META-INF/build-info.properties`。生产整包脚本必须再次读取该值并与包内源码清单
逐字比较；缺失、重复、为 `UNSET` 或不一致都拒绝组包。

1. 使用已经通过测试的同一不可变源码快照生成 JAR、transition Web 和 final Web，并记录各自 SHA-256。
2. 用 `25-stage-backend.sh` 把新 JAR 安装到新版本目录，不覆盖、不切换旧 JAR。
3. 后端仍停止时，先用 `50-install-web.sh --stage transition` 原子切换会议创建关闭的过渡 Web。
4. 再用 `40-activate-backend.sh` 原子切换 JAR 并启动，确认：
   - Spring、Hikari、Redis 初始化成功；
   - 没有 schema、Bean、JWT、微信或部署安全门禁错误；
   - 外访、用印和图纸收发加密密钥门禁通过，日志中没有令牌、scene、
     手机号或身份证明文；
   - `/api/v1/auth/captcha` 返回 HTTP `200` 且 `Result.code=200`；
   - `/doc.html`、`/swagger-ui/**`、`/v3/api-docs/**` 返回 `404`。
5. 不允许通过关闭 `DeploymentSecurityGuard`、弱化 JWT 或开启微信 mock 绕过启动失败。

所有非 dry-run 生产写阶段会先取得 `/run/site-platform-release.lock`，并一直持有到命令退出；这会把
自恢复安装/核验、停服备份、配置、迁移、JAR 暂存、离线工具、后端激活、Web 切换、发布证明和回滚
严格串行化。看到“等待取得生产发布全程互斥锁”时应等待当前命令结束，禁止删除锁文件或并行重试；
持锁进程退出后内核会自动释放租约。

发布停机前，`10-stop-and-backup.sh` 会再取得 watchdog 共用的 `/run/site-platform-watchdog.lock`，再原子创建固定维护锁
`/etc/site-platform/maintenance.lock`，并把服务名和同点备份目录以 SHA-256 绑定。环境补齐、迁移、JAR
暂存、离线访客修复、transition Web 和新后端激活均逐步核对同一把锁；锁缺失、被替换、权限/属主
异常或绑定到其他备份目录时必须停止。新后端只有通过本机、公网、API 文档关闭和日志门禁后才解除锁。
任何失败都保留锁，禁止 watchdog 在半迁移状态拉起后端。完整设计和只读验收见
`docs/生产服务自恢复保护.md`。

`10` 正式执行会检查 APT `Automatic-Reboot` 未启用且 `/run/reboot-required` 不存在。创建维护锁后，
脚本先关闭并核验主服务开机自启，再停止服务；`40`/`90` 只有在完整健康门禁通过后才重新启用并解锁。
维护锁存在期间严禁 ECS 重启、`reboot` 或其他计划重启。若意外重启，主服务应保持 `disabled + inactive`；
如意外成为 `active`，立即停止，并按维护锁、同点备份、离线 worker、表/标记和软链的实际状态决定继续
或 `90` 回滚，禁止直接恢复流量。

`30-visitor-reencrypt.sh` 的 transient worker 通过 `/run/site-platform-offline-worker.state` 记录
`SUBMITTING/RUNNING` 生命周期，并以 `/run/site-platform-offline-worker.lock` 串行化交接、复核和标记删除；
其他生产写阶段看到标记时一律停止。只有 `SUBMITTING` 且 systemd 明确
报告 unit `not-found`、无 job、`MainPID=0` 时才自动闭合。已加载 unit 或 `RUNNING` 残留必须核对日志、
unit 和数据库精确状态，再用 `06-offline-worker-recovery.sh` 的固定确认语受控清理，禁止直接 `rm`
任一 worker 标记或 sidecar lock 文件。

## 七、失败与回滚

触发回滚的条件包括：服务无法启动、验证码/登录失败、连续业务 `500`、权限越权、数据
数量异常、迁移校验失败、文件不可读或无法在维护窗口内完成验收。

回滚原则：

1. 立即停止新流量和写操作，保存失败日志、数据库状态和新 JAR 校验和。
2. 若数据库迁移尚未开始，只恢复旧 JAR/upstream。
3. 若迁移已执行但尚未放开写流量，可在确认旧版本兼容新增结构后临时恢复旧 JAR；仍须
   保留维护状态并完成数据核对，不能把“能启动”视为回滚完成。
4. 若新版本已经接受写入，不手工反向执行 `DROP/ALTER`。应停止写入，评估新旧数据差异，
   使用发布前数据库和文件快照做成对恢复；恢复前另存故障现场快照。
   巡检模板编码迁移虽然不改结构，也只能随应用和数据库快照整体回滚；新应用仍运行时
   不得单独把 `SOCKET_220V / SOCKET_380V` 改回旧编码。
   固定式临边转换也不得通过手工恢复旧模板、类别、权限或删除新增字段来回滚；如果需要恢复转换前
   的开放配置状态，必须使用发布前数据库快照并同时恢复匹配的应用版本和文件存储。
5. 数据库、文件存储和 JAR 必须回到同一时间点。只恢复数据库或只恢复文件可能造成附件
   元数据与物理文件不一致。
6. 回滚后重新验证旧版本核心接口和数据数量，并记录失败原因；问题未关闭前不得重复发布。

`90-rollback.sh` 在缺少维护锁时先创建，有锁时严格核对其与同点备份一致。回滚失败保留锁；只有旧
系统同点恢复完成且本机、公网健康均通过、主服务重新启用开机自启后才解除。维护锁没有 TTL，不得按
时间或重启自动删除。

`90-rollback.sh` 恢复旧服务时必须先有界轮询本机 `127.0.0.1:8080` 验证码接口，再轮询正式域名，
不能用固定数秒等待后的单次公网结果判断启动失败。任一级超时或后续门禁失败都必须确保后端停止，
保留故障现场并写 `ROLLBACK_FAILED`；同点备份中的 Nginx/systemd 已成功解包后不得因健康失败再换回
故障现场配置。只有本机和公网均为 HTTP 200 且业务 `code=200` 后才能写 `ROLLBACK_COMPLETE`。
