# 生产升级与回滚手册

更新时间：2026-08-03。

本文只描述当前代码从旧生产版本升级到 47 表基线的安全步骤。实际主机目录、服务名、
Nginx 配置和密钥必须以生产运维配置为准；仓库不保存这些信息。未经明确生产发布授权，
不得执行本文的写操作。

## 一、当前线上差异

2026-07-31 对 `https://zhihuiyz.xyz` 只读检查确认：

- DNS 和 HTTPS 正常，`/api/v1/**` 已转发到 Spring；
- 线上 Web 静态包使用 `baseURL=/api/v1`，不是前缀配置错误；
- `/api/v1/projects` 等旧接口仍存在；
- `/api/v1/auth/captcha`、统一注册、Web 扫码和微信快捷登录接口不存在；
- 异常响应特征与旧提交 `89f186d` 一致，线上没有运行当前后端。

因此不能通过修改小程序 API 前缀解决。升级至少涉及后端版本、生产数据库版本预检和
生产环境变量；是否同时发布 Web 与小程序应单独验收。

## 二、发布前硬门槛

以下任一条件不满足时停止发布：

1. 已取得明确的生产发布和服务重启授权。
2. 已确认主机、SSH Host、后端服务名、JAR 路径、运行用户、Nginx upstream 和日志路径。
3. 当前发布源码有可追溯版本。不得直接发布无法归属的脏工作树；应先确认变更范围，
   建立提交或保存不可变源码归档，并记录 SHA-256。
4. 已备份生产数据库、文件存储、本地上传目录、当前 JAR、服务配置和 Nginx 配置，
   且备份能在隔离环境读取。
5. 已从生产库只读核对表数、`sys_data_migration`、重复手机号、有效微信绑定、项目角色
   映射和至少一个可恢复的平台管理员，详见 `docs/数据库结构.md`。
6. 已在生产库副本按相同顺序演练迁移和当前 JAR 启动；不使用本地开发库结果代替。
7. 已准备维护窗口、失败判定人、回滚负责人和回滚截止点。
8. 生产环境变量满足 `backend/.env.example`，但真实值只进入部署平台密钥设置：
   - 非 `root` MySQL 账号、非空密码、TLS `DB_URL`；
   - Redis 密码；
   - 独立且至少 32 字节的 JWT 密钥；
   - 正式微信 AppID/AppSecret、HTTPS 域名和回跳地址；
   - `FORWARD_HEADERS_STRATEGY=NATIVE`；
   - `KNIFE4J_ENABLE=false`、`API_DOCS_ENABLED=false`、
     `SWAGGER_UI_ENABLED=false`。

Nginx 必须覆盖设置并向后端传递受信代理头：

```nginx
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
```

后端 `8080` 端口不得直接暴露公网。若实际代理不在 Tomcat 默认受信的回环/私网地址范围，
必须先明确代理地址并收窄配置，不能通过信任任意来源的转发头绕过。

## 三、备份要求

备份名必须包含 UTC/北京时间戳和源版本。至少保存：

- `mysqldump --single-transaction --routines --triggers --events` 生成的完整数据库备份；
- 当前文件存储：本地 `uploads` 或 MinIO 对应 bucket 的版本化快照；
- 当前后端 JAR 及 SHA-256；
- systemd/容器/进程管理配置和实际环境变量键清单（密钥值不得写入仓库或工单正文）；
- Nginx 站点配置；
- 当前 Web 静态目录；
- 发布前接口响应、数据库表数和关键业务数量。

数据库认证应使用服务器受控的客户端配置或密钥注入，不把密码写入命令行、shell 历史、
仓库文件或聊天记录。完成备份后必须至少执行解压、清单和校验和检查；未验证的备份不视为
可回滚备份。

## 四、数据库升级顺序

先停止写流量或进入维护窗口。只有生产预检证明对应迁移尚未应用时，才按以下顺序执行：

1. `20260728_unified_registration_rbac_wechat_login.sql`
2. `20260729_project_multi_role_member_management.sql`
3. `20260729_project_multi_role_permission_cleanup.sql`
4. `20260729_shared_business_module_access.sql`
5. `20260729_wechat_quick_registration_initial_password.sql`
6. `20260730_quality_issue_resilience.sql`
7. `20260801_inspection_template_item_code_alignment.sql`
8. `20260803_role_menu_permission_hierarchy.sql`

完整路径均位于 `backend/src/main/resources/sql/migrations/`。执行规则：

- 禁止执行 `init.sql`、空库初始化脚本和本地测试夹具
  `backend/src/test/resources/sql/fixtures/reset-realistic-business-data.sql`；
- 每份脚本执行后立即检查退出码、表/列/索引和 `sys_data_migration` 标记；
- 项目旧职责无法映射、重复手机号或有效微信绑定冲突时必须中止并人工处理；
- 巡检模板同一模板下旧插座编码与带 `V` 新编码同时有效时必须中止并人工核对；
- 页签菜单迁移前必须核对 `WEB_DOCUMENT / WEB_INSPECTION / WEB_QUALITY`
  父菜单和 `sys_data_migration`；迁移后核对 6 条页签、角色菜单关联以及
  `20260803_ROLE_MENU_PERMISSION_HIERARCHY_V1` 标记；
- 不得为了“继续发布”删除真实用户、角色、绑定或业务数据；
- 全部迁移后核对 47 表基线、角色/项目关联孤儿、唯一约束和平台管理员可恢复性；
- 迁移产生任何不符合预期的告警时，不进入 JAR 切换。

## 五、后端发布

1. 使用已经通过 `mvn clean test` 和 `mvn -DskipTests package` 的同一源码状态生成 JAR，
   记录源码版本、JAR SHA-256、Java 和 Maven 版本。
2. 将新 JAR 上传为新文件名，不覆盖旧 JAR；切换软链接或服务配置前保留旧目标。
3. 先用生产环境变量在不接流量的端口启动，确认：
   - Spring、Hikari、Redis 初始化成功；
   - 没有 schema、Bean、JWT、微信或部署安全门禁错误；
   - `/api/v1/auth/captcha` 返回 HTTP `200` 且 `Result.code=200`；
   - `/doc.html`、`/swagger-ui/**`、`/v3/api-docs/**` 返回 `404`。
4. 再切换 Nginx upstream 或正式服务，执行短时观察后恢复流量。
5. 不允许通过关闭 `DeploymentSecurityGuard`、弱化 JWT 或开启微信 mock 绕过启动失败。

## 六、发布后验收

按顺序保留响应、时间和日志证据：

1. 公共验证码、注册申请状态令牌、错误密码和限流负向用例。
2. 平台管理员登录及 `/auth/user-info`。
3. 普通用户项目列表、资料/巡检/质量菜单和无权接口 `403`；追加“仅台账、
   仅记录、仅质量资料、多角色叠加、停用角色”五类账号的登录、刷新、页签直达与接口验收。
4. Web 注册、审批和登录；小程序正式 AppID 下快捷注册、首次密码和快捷登录。
5. Web 扫码确认、取消、过期、跨浏览器和重复消费。
6. 项目 A/B 隔离、成员暂停/撤权后的全会话失效。
7. 文件上传/预览策略、电箱日检、质量闭环和公开扫码脱敏。
8. Web、H5 和小程序使用同一生产 API；服务器日志没有连续 `500` 或敏感信息响应。

上线最低健康标准：

```text
GET https://zhihuiyz.xyz/api/v1/auth/captcha
HTTP 200
Result.code = 200
```

HTTP `200` 但 `Result.code != 200` 仍判定失败。

## 七、失败与回滚

触发回滚的条件包括：服务无法启动、验证码/登录失败、连续业务 `500`、权限越权、数据
数量异常、迁移校验失败、文件不可读或无法在维护窗口内完成验收。

回滚原则：

1. 立即停止新流量和写操作，保存失败日志、数据库状态和新 JAR 校验和。
2. 若数据库迁移尚未开始，只恢复旧 JAR/upstream。
3. 若迁移已执行但尚未放开写流量，可在确认旧版本兼容新增结构后临时恢复旧 JAR；仍须
   保留维护状态并完成数据核对，不能把“能启动”视为回滚完成。
4. 若新版本已经接受写入，不手工反向执行 `DROP/ALTER`。应停止写入，评估新旧数据差异，
   使用发布前数据库和文件快照做成对恢复；恢复前另存故障现场快照。
   巡检模板编码迁移虽然不改结构，也只能随应用和数据库快照整体回滚；新应用仍运行时
   不得单独把 `SOCKET_220V / SOCKET_380V` 改回旧编码。
5. 数据库、文件存储和 JAR 必须回到同一时间点。只恢复数据库或只恢复文件可能造成附件
   元数据与物理文件不一致。
6. 回滚后重新验证旧版本核心接口和数据数量，并记录失败原因；问题未关闭前不得重复发布。
